## 做了什么

服务端、隔离方式和 S1 相同：

- 端口 8191；
- `CLAUDE_CONFIG_DIR` 指向临时目录；
- 加 `--no-session-persistence`；
- `env -u CLAUDE_CODE_REMOTE_SESSION_ID`。

先用 `teamflow setup --home $W/home6 --clients claude` 写一个临时 HOME，再用 `teamflow claude-flags --home $W/home6` 得到：

```text
--settings $W/home6/.config/teamflow/claude-headless-settings.json --mcp-config $W/home6/.config/teamflow/claude-mcp.json --allowedTools mcp__teamflow__*
```

`claude-headless-settings.json` 里有：

- `permissions.allow: ["mcp__teamflow__*"]`；
- 4 个 exec form hook（SessionStart、UserPromptSubmit、Stop、SessionEnd），都是 `teamflow hook <事件> --client claude --cred <abs>`。

四种运行：

- **S6a**：普通 `-p`，加上 `$FLAGS --strict-mcp-config`。
- **S6c**：普通 `-p`，`HOME` 指向临时目录，hooks 来自 setup 写的 `~/.claude/settings.json`。为了遵守"一律 `--settings`/`--mcp-config --strict-mcp-config`"，这两个参数传的是空文件。
- **S6b**：`--bare $FLAGS --strict-mcp-config`。
- **S6b'**：同 S6b，但在 headless settings 里加一个占位的 apiKeyHelper（返回无效 key）。目的是越过"找不到认证方式"那一步，看 hooks 和 MCP 会不会执行。

S6a 的提示词是提问式的：先不调用工具，根据会话开始时看板提供的数据回答"我是谁、进行中的任务、请我帮忙的困难"，再调用 inbox 核对。逐字复述上下文的提示会被模型安全策略拒绝，见 S1 发现 6。

**本轮复测（修复之后，2026-10-02 12:28，端口 8194）**：

- 改用非 editable 安装的 teamflow，`teamflow setup --home <临时目录> --clients claude`。
- `claude -p` 的 hooks 和 allow 规则读用户级 settings，MCP 用 setup 生成的 `claude-mcp.json`，加 `--strict-mcp-config`。
- 跑了两次：
  - 第一次：注入、inbox、claim_task、Stop 上报；
  - 第二次：人通过 DEV 端点接受之后，用 get_item 读正文。
- 完整事件序列见 [evidence/E2E_run1.txt](evidence/E2E_run1.txt) 和 [evidence/E2E_run2_dev.txt](evidence/E2E_run2_dev.txt)。

## 结果

摘录见 [evidence/S6_headless.txt](evidence/S6_headless.txt)。

- **S6a / S6c**：
  - stream-json 里有 SessionStart、UserPromptSubmit、Stop 的 hook_started；
  - 完整调试日志里 `teamflow hook` 分别出现 4 次和 2 次，都有 `SessionEnd:other [… teamflow hook session-end …]`；
  - 服务端收到 session-start、2 次 batch（Stop 的 turn_end 和 SessionEnd 的 end）和 me/delta，全部 200；
  - 模型回答"我是 alice；进行中 T-50、T-53；请我帮忙 B-7（来自 bob）"，`permission_denials=[]`。
- **S6b / S6b'（bare）**：
  - stream-json 里**没有任何 hook_started**，调试日志里 `teamflow hook` 出现 0 次；
  - 服务端只收到 MCP 的 4 个请求（discover、prompts/list、resources/list、tools/list），没有任何 `/api/v1/hooks/*`；
  - 模型请求因认证失败结束。
- **本轮复测**：
  - 第一次运行里，SessionStart 注入了 `待您接受 T-55（来自 bob 的 Codex…）`，模型如实转述；
  - inbox、claim_task(T-53) 成功，claim_task(T-51) 返回 `needs_human：…`；
  - Stop 之后服务端收到 2 次 batch；本地会话文件写了 `ended`，`spool/sent` 有 2 个标记。

## 结论与发现

1. **普通 `claude -p` 通过。** 不论 hooks 来自 `--settings` 还是用户级 settings，4 个 hook 都执行。注入的内容能进到上下文里被模型使用；MCP 的读写工具都不审批。
2. **bare 模式下 teamflow 的 hooks 全部失效，要改 plan 6.8。**
   - plan 6.8 设想 `claude --bare -p $(teamflow claude-flags)` 同时带上 hooks 和 MCP；实测只带上了 MCP 和 allow 规则。
   - 结果是 bare 会话里没有 SessionStart 注入，也没有 turn_end 和 end 上报。
   - 服务端看到的是"有 MCP 调用、没有 hook"，和"Codex hooks 未信任"的症状一样，提醒逻辑要能区分这两种情况。
   - 这与 `claude --help` 对 `--bare` 的说明一致（"skip hooks"）。cc_headless.md 写的是"跳过 hooks 的 auto-discovery"，容易被读成 `--settings` 里显式给的 hooks 仍会执行，实测并不执行。
   - 可选做法二选一：
     - `claude-flags` 额外输出 `--append-system-prompt-file <CLI 用缓存渲染的看板摘要>`，把注入补上；
     - 接受 bare 只有 MCP，在文档里写明，脚本开工时先调用 inbox。
   - cc_headless.md 第 70 行说 bare 将来会成为 `-p` 的默认，到那时普通 `-p` 也会丢掉 hooks。这件事要在冻结命令串之前定下来。
3. **bare 在本容器无法认证。** 本容器用 OAuth 登录，bare 只认 `ANTHROPIC_API_KEY` 或 `apiKeyHelper`。bare 下的工具调用要在成员电脑上补测。
4. **脚本要把 stdin 重定向到 `/dev/null`。** 不重定向时，`claude -p` 有时会先打印 `Warning: no stdin data received in 3s…`，平白多等 3 秒。文档里的无头示例统一写成 `claude -p … < /dev/null`。
5. **沙箱依赖：已在 doctor 里检查。**
   - setup 默认打开沙箱。但在缺 bubblewrap、socat 的 Linux 上，Claude Code 只警告一句 `Sandbox disabled … Commands will run WITHOUT sandboxing`，然后照常运行。plan 6.1 的"凭据保护：sandbox.credentials"在这类机器上等于没有。
   - 现在 `teamflow doctor` 在 Linux 上发现 `sandbox.enabled` 为 true 而缺 `bwrap` 或 `socat` 时，会标"失败"并给出安装命令。本轮在本容器实测的输出见 evidence。
   - 测试：`test_cli_setup.py::test_doctor_sandbox_deps_missing_on_linux`、`::test_doctor_sandbox_check_rules`。
6. **兜底命令已补齐，但和沙箱有冲突。**
   - instructions 里提到的 `teamflow note`、`teamflow done` 现在都有了，另加了 `teamflow block`，走跨包约定的 REST 端点。本轮打真实服务端跑通，见 [evidence/E2E_fallback_cli.txt](evidence/E2E_fallback_cli.txt)。
   - 冲突在于：沙箱的凭据屏蔽真正生效时，agent 从 Bash 跑 `teamflow inbox/note/done` 会读不到凭据。plan 6.4 的加固和 6.8 的"MCP 不可用改走 CLI"互相冲突。
   - CLI 现在读不到凭据时会提示"可能被沙箱屏蔽"，但冲突本身还要在 plan 里定。本机没有 bwrap，没有实测。
7. **`$(teamflow claude-flags)` 不加引号时，`mcp__teamflow__*` 会做路径名展开。** 当前目录恰好有以它开头的文件时，参数会被替换掉。文档推荐 `eval "claude -p … $(teamflow claude-flags --quoted)"`。
8. **setup 合并写入的 `<home>/.claude.json` 能保留下来。** Claude Code 启动时会重写这个文件（先备份），`mcpServers.teamflow` 被保留。Claude Code 正在运行时并发写入的情况没有测。

## 需要成员电脑补测

1. **bare 模式下的工具调用**：由有 `ANTHROPIC_API_KEY`（或 `apiKeyHelper`）的成员，在 `git init` 过的临时目录里跑：
   ```bash
   claude --bare -p "调用 teamflow 的 inbox 工具，用一行回答 me 字段的值" $(teamflow claude-flags) --output-format stream-json --verbose < /dev/null
   ```
   确认三件事：
   - 工具调用成功；
   - `permission_denials` 为空，即 `--allowedTools` 在 bare 下生效；
   - 仍然没有 hook_started。
2. **`codex exec`**：按 `docs/m0.md`「成员电脑补测清单」用 `spike/codex_check.sh` 跑，确认：
   - 不审批；
   - hooks 执行，注入以 `【teamflow` 开头；
   - hook 的 `session_id` 与 `thread.started` 的 thread_id、`_meta["x-codex-turn-metadata"].session_id` 三者一致。
3. **普通 `claude -p` 读真实用户级配置**：在成员电脑上不加任何 flag 跑一次，确认 4 个 hook 和 user scope MCP 都生效。本容器为了不碰 `~/.claude`，user scope MCP 是用内容相同的 `claude-mcp.json` 加 `--strict-mcp-config` 代替的。
4. **沙箱依赖检查**：Linux 成员运行 `teamflow doctor`，没装 bwrap 或 socat 时应当标红。装好后，在沙箱里让 agent 跑一次 `teamflow inbox`，看能不能读到凭据，用来给第 6 条的冲突提供实测依据。
