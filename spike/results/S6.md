# S6 无头运行（Claude Code 部分）

结论：**部分通过**。

| 方式 | 结论 | 要点 |
|---|---|---|
| 普通 `claude -p` + `--settings`（`$(teamflow claude-flags)`，不加 `--bare`） | **通过** | 4 个 hook 都执行；SessionStart 的注入内容模型能复述；MCP 工具调用成功，不审批 |
| 普通 `claude -p` 读 setup 写入的用户级 settings（临时 HOME） | **通过** | 用户级 hooks 照常执行，注入内容模型能复述 |
| `claude --bare -p $(teamflow claude-flags)` | **工具调用无法在此验证；hooks 不通过** | 本容器没有 `ANTHROPIC_API_KEY`，模型请求必然失败；但能确认 **bare 模式下 `--settings` 里的 hooks 一条都不执行**，`--mcp-config` 的 MCP 仍然连接 |

Codex 的 `codex exec` 本机没有 Codex，**无法在此验证**。

## 做了什么、命令

服务端、隔离方式和 S1 相同（端口 8191，`CLAUDE_CONFIG_DIR` 临时目录，`--no-session-persistence`，`env -u CLAUDE_CODE_REMOTE_SESSION_ID`）。

先把 `teamflow setup` 写进一个临时 HOME，得到 claude-flags 用的两个文件：

```bash
HOME=$W/home6 teamflow setup --home $W/home6 --clients claude --cred $W/cred/credentials.json --bin /home/user/team-flow/.venv/bin/teamflow
#   已写入 $W/home6/.claude/settings.json、$W/home6/.claude.json、
#         $W/home6/.config/teamflow/claude-headless-settings.json、claude-mcp.json
HOME=$W/home6 teamflow claude-flags --home $W/home6
#   --settings $W/home6/.config/teamflow/claude-headless-settings.json --mcp-config $W/home6/.config/teamflow/claude-mcp.json --allowedTools mcp__teamflow__*
```

`claude-headless-settings.json` 里有 `permissions.allow: ["mcp__teamflow__*"]`，以及 SessionStart、UserPromptSubmit、Stop、SessionEnd 四个 exec form hook，都是 `teamflow hook <事件> --client claude --cred <abs>`。

**S6a：普通 `-p`**

```bash
FLAGS=$(HOME=$W/home6 teamflow claude-flags --home $W/home6)
TFSTATE=$W/tfstate6a run_nested.sh s6a_plain cccccccc-0000-4000-8000-00000000000a "$P" -- $FLAGS --strict-mcp-config
```

提示词：`先不要调用任何工具，只根据会话开始时 teamflow 团队看板提供的数据回答：我（看板上的用户名）是谁？进行中的任务编号有哪些？请我帮忙的困难编号是什么？如果会话开始时没有收到看板数据，就回答"没有收到"。回答完后再调用 teamflow 的 inbox 工具，用一行说明 inbox 里 me 字段的值是否与前面一致。`

**S6c：普通 `-p`，读用户级 settings**

```bash
cd $W/proj && env -u CLAUDE_CODE_REMOTE_SESSION_ID -u CLAUDE_CONFIG_DIR HOME=$W/home6 TEAMFLOW_STATE_DIR=$W/tfstate6c \
  claude -p "$P" --settings settings_empty.json --mcp-config mcp_empty.json --strict-mcp-config \
  --output-format stream-json --verbose --no-session-persistence --session-id cccccccc-0000-4000-8000-00000000000c
```

为了遵守"一律 `--settings`/`--mcp-config --strict-mcp-config`"，这里传的是空文件。hooks 来自临时 HOME 下 setup 写的 `~/.claude/settings.json`；真实的 `/root/.claude` 没有被读写。

**S6b：bare**

```bash
TFSTATE=$W/tfstate6b run_nested.sh s6b_bare cccccccc-0000-4000-8000-00000000000b "$P" -- --bare $FLAGS --strict-mcp-config
# 再试一次：在同一份 headless settings 里加一个占位的 apiKeyHelper（echo 一个无效 key），
# 目的是让启动流程越过"找不到认证方式"那一步，看 hooks 和 MCP 会不会执行
TFSTATE=$W/tfstate6b2 run_nested.sh s6b_bare_dummykey ... -- --bare --settings settings_s6b_dummykey.json \
  --mcp-config $W/home6/.config/teamflow/claude-mcp.json --allowedTools "mcp__teamflow__*" --strict-mcp-config
```

## 原始输出摘录

**S6a（普通 `-p` + `--settings`）**，stream-json 事件按顺序：

服务端日志（这次运行的全部 9 条，都是 200，没有 3xx）：
```
POST /api/v1/hooks/session-start  sess=cccccccc-…-00000000000a  ua=teamflow-cli
POST /mcp/ server/discover | prompts/list | resources/list | tools/list | tools/call(inbox)   pv=2026-07-28
POST /api/v1/hooks/batch ×2   ← Stop 的 turn_end 和 SessionEnd 的 end，由分离的 flush 上传
GET  /api/v1/me/delta           ← flush --refresh 刷缓存
```
SessionEnd 执行的证据有三处：
- 调试日志 `SessionEnd:other [/home/user/team-flow/.venv/bin/teamflow hook session-end --client claude …]`；
- 本地会话文件 `sessions/claude-cccccccc-…-00000000000a.json` 里写了 `"ended": 1790910773.50`；
- `spool/sent/` 下有 2 条已发送标记。

stream-json 在 result 之后就结束了，所以里面看不到 SessionEnd 的事件。注意 `-p` 下 SessionEnd 的 reason 是 `other`。

**S6c（用户级 settings）**：与 S6a 相同。SessionStart 有输出，UserPromptSubmit 和 Stop 都执行。服务端收到 session-start、batch×2、me/delta。模型回答 `你是 alice。进行中的任务编号是 T-50 和 T-53。……请你帮忙处理 B-7（来自 bob），以及有 1 条 B-7 的评论等你转发。`

**S6b（bare，没有 key）**，原文：
```

[ERROR] API error (attempt 1/11): Could not resolve authentication method. Expected one of apiKey, authToken, credentials, config, or profile to be set. Or for one of the "X-Api-Key" or "Authorization" headers to be explicitly omitted

同一次运行里：MCP 照常连接（`mcp runtime arm: v2 (source: default)`、`negotiatedProtocolVersion 2026-07-28`，服务端收到 discover、prompts、resources、tools/list 4 条 200）。**stream-json 里没有任何 hook_started**，服务端没有收到 `/api/v1/hooks/session-start`，状态目录里除了 log 什么都没有。

**S6b'（bare，占位 apiKeyHelper）**：
```
SYSTEM api_retry {"attempt": 1, "max_retries": 10, "error_status": 401, "error": "authentication_failed"}
[ERROR] API error (attempt 1/11): 401 401 {"type":"error","error":{"type":"authentication_error","message":"API key is invalid."}}
调试日志里 "teamflow hook" 出现 0 次，"SessionEnd:other" 0 次，"Hooks: Checking first line" 0 次
  （对照 S6c 的调试日志："Hook SessionStart (…/teamflow hook session-start …)"、"SessionEnd:other […/teamflow hook session-end …]" 都有）

非 bare 模式下，SessionStart hook 在 init 之前、第一次模型请求之前就执行了。bare 模式下同一个位置什么都没有执行，所以"hook 没执行"不是认证失败造成的。这和 `claude --help` 对 `--bare` 的说明一致："skip hooks (those defined in settings and by installed plugins …)"。cc_headless.md 的说法是"跳过 hooks 的 auto-discovery"，容易被理解成 `--settings` 里显式给的 hooks 仍然执行，但实测不执行。

## 结论与发现

1. **普通 `claude -p` 通过。** 不论 hooks 来自 `--settings` 还是用户级 settings，4 个 hook 都执行；注入内容进到上下文里，模型能用；MCP 写读都不审批。
2. **bare 模式下 teamflow 的 hooks 全部失效（需要改 plan 6.8，只报告，没改代码）。**
   - plan 6.8 设想 `claude --bare -p $(teamflow claude-flags)` 同时带上 hooks 和 MCP，实测只带上了 MCP 和 allow 规则。
   - 于是 bare 会话里：没有 SessionStart 注入，没有 turn_end 和 end 上报，服务端看到的是"有 MCP 调用、没有 hook"，和"Codex hooks 未信任"的症状一样，提醒逻辑要能区分。
   - 可选做法：
     - `claude-flags` 额外输出 `--append-system-prompt-file <CLI 用缓存渲染的看板摘要文件>`，补上注入；
     - 或者接受 bare 只有 MCP，在文档里写明，让脚本开工时先调用 inbox。
   - 另外，bare 将来会成为 `-p` 的默认（cc_headless.md 70 行），到时普通 `-p` 也会丢掉 hooks。这件事要在冻结命令串之前定下来。
3. **bare 在本容器无法认证**：容器的登录是 OAuth，从 `/home/claude/.claude/remote/.oauth_token` 读取；bare 只认 `ANTHROPIC_API_KEY` 或 `apiKeyHelper`，本机都没有。bare 下的工具调用要在成员电脑上补测。
4. **脚本要把 stdin 重定向到 `/dev/null`**：不重定向时，`claude -p` 有时会在 stderr 打印 `Warning: no stdin data received in 3s, proceeding without it. If piping from a slow command, redirect stdin explicitly: < /dev/null to skip, or wait longer.`，平白多等 3 秒。文档里的无头示例统一写成 `claude -p … < /dev/null`。
5. **setup 默认打开的沙箱在缺依赖的 Linux 上不生效**：S6c 读到 setup 写的 `sandbox.enabled: true`，stderr 原文是 `⚠ Sandbox disabled: sandbox is enabled but dependencies are missing: bubblewrap (bwrap) not installed, socat not installed … Commands will run WITHOUT sandboxing. Network and filesystem restrictions will NOT be enforced.`
   - plan 6.1 的"凭据保护：sandbox.credentials"在这类机器上等于没有。
   - 建议 doctor 在 Linux 上检查 `bwrap` 和 `socat`，缺了就标"失败"，并给安装命令。
6. **`$(teamflow claude-flags)` 不加引号时 `mcp__teamflow__*` 会做路径名展开**。当前目录恰好有以 `mcp__teamflow__` 开头的文件时，参数会被替换掉。概率很低，文档里提一句，或者推荐 `eval "claude -p … $(teamflow claude-flags --quoted)"`。
7. setup 直接合并写 `<home>/.claude.json` 之后，Claude Code 启动时会重写这个文件（先备份），`mcpServers.teamflow` 被保留下来了。CLI 报告里不确定项 8 的担心在"Claude Code 没在运行"时不成立；Claude Code 正在运行时并发写入的情况没有测。
8. 验证中没有改任何代码。

## 需要成员电脑补测

1. 有 `ANTHROPIC_API_KEY`（或 `apiKeyHelper`）的成员，在 `git init` 过的临时目录里跑：
   ```bash
   claude --bare -p "调用 teamflow 的 inbox 工具，用一行回答 me 字段的值" $(teamflow claude-flags) --output-format stream-json --verbose < /dev/null
   ```
   确认三件事：工具调用成功、`permission_denials` 为空（`--allowedTools` 在 bare 下生效）、仍然没有 hook_started。
2. `codex exec --skip-git-repo-check --json "调用 teamflow 的 inbox 工具……" < /dev/null`：
   - 从 `thread.started` 取出 thread_id，与服务端登记的会话比对；
   - 确认不审批，hooks 执行并且注入以 `【teamflow` 开头。
3. 成员电脑上普通 `claude -p`（不加任何 flag，读真实的用户级配置）跑一次，确认 4 个 hook 和 user scope MCP 都生效。在本容器里，这一步为了不碰 `~/.claude`，是用临时 HOME 加空的 `--mcp-config --strict-mcp-config` 做的，所以 user scope MCP 那一半没有覆盖到。
4. Linux 成员运行 `teamflow doctor`，看沙箱依赖缺失时是否标红（需要先实现第 5 条建议）。
