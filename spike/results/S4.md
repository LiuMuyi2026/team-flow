# S4 hook 延迟（服务端正常、慢 3 秒、不可达）

结论：**部分通过**。

- **CLI 基准在本容器通过**：Claude Code 的 exec form，以及 Codex 用会话 shell 的 `sh -c` / `bash -c`，在三种服务端情况下 4 个 hook 的 p95 全部达标。服务端慢或不可达时，Stop 和 SessionEnd 没有变慢：分离进程确实不阻塞 hook，Claude Code 真实客户端也不等它。
- **两处要注意**：
  - UserPromptSubmit 的 p95 是 24–29ms，离 30ms 只差几毫秒，主要花在 Python 解释器启动上，换到成员的 macOS 上可能超标；
  - Codex 走 `$SHELL -lc` 退回路径时，本容器的 profile 让每个 hook 多出约 150ms，UserPromptSubmit 超标。
- **真实 Codex 的延迟无法在此验证**，要在成员电脑上补测。

## 做了什么、命令

- 服务端：`uvicorn teamflow_server.app:app --port 8192 --workers 1`。S4 的观测日志写到 `spike/out/s4.log.jsonl`，S2 的证据留在 `s2.log.jsonl`，两者不混。三种情况：
  - 正常：`TEAMFLOW_FAULT_DELAY_MS=0`；
  - 慢：`TEAMFLOW_FAULT_DELAY_MS=3000`，作用于 `/api/v1/hooks/*` 和 `/api/v1/me/*`，用 curl 实测 batch 要 3.01 秒；
  - 不可达：`http://127.0.0.1:9`，没人监听，连接被拒。
- teamflow 用单独 venv 里非 editable 安装的版本，等同 `uv tool install`。共享的 `.venv` 里有 editable finder，会让每次启动多出约 19ms，不代表成员电脑。基准脚本也用这个 venv 的 Python 跑，`python -c pass` 基线才可比。
- 执行方式：
  - `exec`：Claude Code 的 exec form，直接执行 teamflow；
  - `sh`：`/bin/sh -c '<命令串>'`，本机的 sh 是 dash；
  - `bash`：`bash -c`；
  - `login`：`$SHELL -lc`（`$SHELL=/bin/bash`），对应 Codex 没有会话 shell 时的退回路径；
  - 本机没有 zsh。
- 客户端：exec 配 Claude，其余配 Codex（hook 输入按各自的格式）。每个事件 50 次，spawn 开着，也就是 Stop 和 SessionEnd 真的会拉起分离的 flush。

```bash
# spike/bench_hooks.py 新加了 --shell bash|zsh
$V/bin/python spike/bench_hooks.py --api http://127.0.0.1:8192 --token-claude tf_pat_dev_alice --token-codex tf_pat_dev_bob \
   --n 50 --clients claude --shell exec --bin $V/bin/teamflow --json      # 再换 --clients codex --shell sh|bash|login
# 慢：服务端以 TEAMFLOW_FAULT_DELAY_MS=3000 重启后同上；不可达：--api http://127.0.0.1:9
```

本机有 4 核，Python 3.11.15。跑基准时没有别的进程在占用 CPU，loadavg 约 0.4。

## 关键：服务端慢或不可达时，Stop / SessionEnd 不变慢

1. **基准里的 Stop**：正常时 p95 是 57.9 / 64.9 / 59.8，慢 3s 时 56.2 / 53.1 / 61.8，不可达时 66.1 / 58.1 / 59.8，三种情况看不出差别。hook 返回时 stdout 管道就已经 EOF 了，基准用 `subprocess.run(stdout=PIPE)` 计时，如果子进程继承了管道，这里会等满 3 秒以上。
2. **※ 慢 3s 时 SessionEnd 的 p95 到了 96.1 / 87.6**，原因是基准的突发压力，不是阻塞：
   - 每次 Stop / SessionEnd 都拉起一个分离的 flush；服务端慢时，每个 flush 要活 3–6 秒（拿锁最多等 3 秒，请求本身 3 秒）。50 次 Stop 加 50 次 SessionEnd 在几秒内连发，采样到**最多 100 个分离的 flush 同时存在**（4 核机器上的 CPU 争用）。
   - 同样条件只跑 `stop,session-end` 复测：Stop 44.1 / 53.6 / 58.8，SessionEnd 39.9 / **54.9** / 63.0。
   - 加 `--no-spawn`，不拉起 flush：Stop 46.2 / 57.2，SessionEnd 32.5 / 43.8。
   - 真实使用里每回合才有一次 Stop，不会出现这种突发。
3. **默认 flush 预算下的分离**：不设 `TEAMFLOW_FLUSH_BUDGET`，默认 60 秒，服务端不可达。
   - Stop hook **45.8ms** 就返回了。
   - 分离的 flush 在后台又活了约 **34.7 秒**：按 5、10、20 秒退避重试 3 次，期间一直拿着锁。
   - 结束后 spool 里留着 `turn_end` 和 `start` 两条，`attempts=4`，等下次 flush 补发。错误写进了状态目录的 log，hook 没有任何输出。
4. **Claude Code 真实客户端**：服务端慢 3 秒时嵌套跑 `claude -p "只回复 OK"`，hooks 用的是 setup 生成的那份，见 S2。
   - 整次运行 4.05 秒，服务端正常时是 3.66 秒。差出来的主要是 SessionStart 的 1 秒 HTTP 超时：log 里是 `session-start net: TimeoutError`，那次没有缓存，所以不注入。
   - `claude` **退出时还有 3 个分离的 flush 活着**，etimes 0–2 秒：一个是 UserPromptSubmit 发现缓存过期拉起的 `--refresh`，一个是 Stop 拉起的 `--refresh`，一个是 SessionEnd 拉起的 flush。
   - 之后服务端日志在 +1.2 秒和 +4.2 秒各收到一次 `hooks/batch`，都带 `fault_delay_ms:3000`、状态 200。
   - 结论：Claude Code 不等分离进程。Codex 这边，源码里 hook 正常结束后不清理它留下的子进程（`command_runner.rs:281`）；但 Codex 要等 stdout 和 stderr 都 EOF（`wait_with_output`），我们的分离进程三个 fd 都接了 /dev/null，所以同样不会被等。

## 发现与建议

1. **UserPromptSubmit 的 30ms 余量很小**：
   - p95 是 23.4–28.8ms，偶发的 max 到了 38–45ms，基线 `python -c pass` 的 p95 已经约 20ms。
   - macOS 上 Python 启动通常更慢，有安全扫描和 dyld 的开销，成员电脑上很可能超标。
   - 退路按冷启动开销从小到大：
     - 解释器加 `-I -S` 这类参数，但 venv 的 site-packages 要靠 site 才能找到，需要改启动方式；
     - 把 prompt 的快速路径做成更小的入口模块；
     - 接受 p95 在 30–40ms。
   - 这个问题在冻结命令串之前就要决定，因为命令串里的可执行文件路径会进 Codex 的信任哈希。
2. **Codex 的 `$SHELL -lc` 退回路径**：本容器的 `/etc/profile.d` 比较重（有 nvm 等），每个 hook 多出约 150ms：
   - UserPromptSubmit 超标；
   - 慢服务端时 SessionStart 到了 1.27 秒，超标；
   - Stop 和 SessionEnd 还在 Codex 的 400ms 之内。

   加上 S2 发现的问题（profile 有输出时 Stop 每回合都被 Codex 判 Failed），这条路径要在成员电脑上确认什么时候会走到：

   - 源码里只在没有会话 shell 时才会走；
   - doctor 已经把 `-lc` 有输出标成失败，但耗时没有提示。
3. **服务端慢时分离进程会堆积**：服务端慢时，每个 Stop / SessionEnd 拉起的 flush 要活 3–6 秒，拿不到锁的那些等满 3 秒才退出。正常节奏下不是问题。如果以后要省进程，可以在 hook 里先 `stat` 一下 spool 锁，锁很新就不再拉起 flush（只多一次 stat）。这是建议，没有改。
4. **SessionStart 最坏情况**：git 读取 300ms 加 HTTP 1s，总共约 1.3 秒，会超过 1.2 秒，CLI 报告里已经提过。本次 git 很快，慢服务端时 p95 是 1.09–1.10 秒，在目标之内。
5. 不可达只测了「连接被拒」。本容器的出站 TCP 会被透明代理接住，`10.255.255.1` 也能立即连上，模拟不出丢 SYN、一直挂起的情况。不过「连上之后不回应」已经由慢 3s 覆盖，SessionStart 的 HTTP 有 1 秒硬上限，Stop 和 SessionEnd 不联网。

## 需要成员电脑补测

1. **CLI 基准**：在成员的 Mac 或 Linux 上，用 `uv tool install` 装好的 teamflow 跑同样的矩阵。服务端在仓库里本机起，加 `TEAMFLOW_FAULT_DELAY_MS=3000` 再跑一遍：

   ```bash
   P=$(head -1 "$(command -v teamflow)" | sed 's/^#!//')   # uv tool 自带的 Python
   for s in exec sh zsh bash login; do
     $P spike/bench_hooks.py --api http://127.0.0.1:8100 --token-claude <claude PAT> --token-codex <codex PAT> \
        --n 50 --shell $s --bin "$(command -v teamflow)" --json > bench-$s.txt
   done
   ```

   macOS 的 `$SHELL` 一般是 zsh，`--shell zsh` 和 `--shell login` 是最接近 Codex 的两种。
2. **真实 Codex**：在 `codex exec --json` 下分别对正常、慢 3s、不可达三种服务端各跑 10 次，看 `turn.completed` 前后的总耗时，如果在界面或日志里能看到 Codex 记录的 hook 耗时，一并记下（源码里每次 hook 运行的结果都带 `duration_ms`，见 `command_runner.rs` 的 `finish_command_run`）。要求 Stop 和 SessionEnd 不随服务端变慢。
3. **真实 Claude Code**：在交互模式下开 `claude --debug hooks`，各跑几轮，看 hook 耗时。
4. 如果 UserPromptSubmit 的 p95 超过 30ms，按「发现与建议」第 1 条在冻结命令串之前定下退路。
