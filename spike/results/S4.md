## 做了什么、命令

- **teamflow 的安装**：新建独立 venv，非 editable 安装 `cli/`（`uv venv --python /usr/bin/python3.11 v && uv pip install --python v/bin/python ./cli`），等同于 `uv tool install`。共享 `.venv` 里的 editable finder 每次启动会多出约 19ms，不代表成员电脑。基准脚本也用这个 venv 的 Python 跑，这样 `python -c pass` 基线才可比。
- **服务端**：`uvicorn teamflow_server.app:app --port 8194 --workers 1`，三种情况：
  - 正常；
  - 慢：重启时加 `TEAMFLOW_FAULT_DELAY_MS=3000`，作用于 `/api/v1/hooks/*` 和 `/api/v1/me/*`；
  - 不可达：`--api http://127.0.0.1:9`，连接被拒。
- **执行方式**：
  - `exec`：Claude Code 的 exec form；
  - `sh`：`/bin/sh -c '<命令串>'`，本机的 sh 是 dash；
  - `bash`：`bash -c`，模拟 Codex 的会话 shell。
- **每格 50 次**，spawn 开着，也就是 Stop 和 SessionEnd 真的会拉起分离的 flush。
- **UserPromptSubmit 的 4 条路径**（`spike/bench_hooks.py` 文档串）：
  - `prompt`：缓存新鲜、没有新条目；
  - `prompt:stale`：缓存过了 60 秒；
  - `prompt:emit`：有新的「需要我」条目，输出增量；
  - `prompt:stale+emit`：两者都有。

  后三条每次运行前都重写缓存和会话状态。「拉起」列统计 hook 拉起分离进程的次数。
- **机器**：4 核，Python 3.11.15，跑基准时 loadavg 0.1–0.65，没有别的负载。

```bash
for st in normal slow down; do   # slow：服务端以 TEAMFLOW_FAULT_DELAY_MS=3000 重启；down：--api http://127.0.0.1:9
  for combo in "exec claude" "sh codex" "bash codex"; do set -- $combo
    $V/bin/python spike/bench_hooks.py --api http://127.0.0.1:8194 --token-claude <claude PAT> --token-codex <codex PAT> \
      --n 50 --clients $2 --shell $1 --bin $V/bin/teamflow --json
  done
done
```

修复做了三件事：

## 关键：服务端慢或不可达时，Stop 和 SessionEnd 不变慢

1. **基准里看不出三种状态的差别。**
   - Stop 的 p95：正常 48.0–54.5，慢 3s 48.8–61.7，不可达 56.6–57.9；
   - SessionEnd 的 p95：正常 43.6–55.5，慢 3s 47.3–54.8，不可达 42.3–53.6；
   - 基准用 `subprocess.run(stdout=PIPE)` 计时，hook 返回时 stdout 管道就已经 EOF 了。如果分离出去的 flush 继承了管道，这里会等满 3 秒以上。
2. **第一轮慢 3s 时 SessionEnd p95 到过 96/88，这次没有复现**（47.3–54.8）。第一轮已经查明是基准突发压力造成的：
   - 50 次 Stop 和 50 次 SessionEnd 在几秒内连发，最多 100 个分离的 flush 同时存在，4 核机器上抢 CPU；
   - 真实使用里每回合只有一次 Stop，不会这样集中。
3. **默认 flush 预算下的分离**（第一轮实测，不设 `TEAMFLOW_FLUSH_BUDGET`，默认 60 秒，服务端不可达）：
   - Stop hook 45.8ms 就返回了；
   - 分离的 flush 在后台又活了约 34.7 秒，按 5、10、20 秒退避重试，期间一直拿着锁；
   - 结束后 spool 里留着 `turn_end` 和 `start`，`attempts=4`，等下次补发；
   - hook 没有任何输出。
4. **真实客户端**：
   - **Claude Code**，第一轮：服务端慢 3 秒时嵌套跑 `claude -p "只回复 OK"`，整次 4.05 秒，正常时 3.66 秒。差出来的主要是 SessionStart 的 1 秒 HTTP 超时。`claude` 退出时还有分离的 flush 活着，说明它不等这些进程。
   - **本轮的嵌套端到端**：Stop 和 SessionEnd 之后，服务端收到 2 次 batch 和 1 次 me/delta，全部 200，见 [evidence/S3_after_fix_e2e.txt](evidence/S3_after_fix_e2e.txt)。
   - **Codex**：源码里要等 stdout 和 stderr 都 EOF（`wait_with_output`）。我们的分离进程三个 fd 都接 `/dev/null`，所以同样不会被等。这一条要在成员电脑上实测。

## 发现与建议

1. **UserPromptSubmit 在 Codex 一侧没有余量。**
   - Claude exec 的 p95 在 18.6–27.7；Codex `sh -c` 在 23.5–29.2，`bash -c` 在 25.0–32.3。
   - 基线 `python -c pass` 的 p95 本身就有 16–26。
   - macOS 上 Python 启动通常更慢（安全扫描、dyld），成员电脑上很可能超过 30。
   - 退路按冷启动开销从小到大：
     - 加 `-I -S` 这类解释器参数，但这样需要改启动方式，因为 venv 的 site-packages 要靠 site 才能找到；
     - 把 prompt 的快速路径做成更小的入口模块；
     - 接受 p95 在 30–40ms。
   - 这件事要在冻结命令串之前定：可执行文件的路径和参数会进 Codex 的信任哈希。
2. **Codex 的 `$SHELL -lc` 退回路径**：第一轮实测本容器的 `/etc/profile.d`（nvm 等）让每个 hook 多出约 150ms。
   - UserPromptSubmit p95 约 185–190，超标；
   - 慢服务端时 SessionStart 到了 1.27 秒，超标；
   - Stop 和 SessionEnd 还在 Codex 的 400ms 之内。

   加上 S2 的发现（profile 有输出时，Stop 每回合都被 Codex 判失败），要在成员电脑上确认什么时候会走到这条路径。
3. **SessionStart 的最坏情况**：git 读取 300ms 加 HTTP 1 秒，约 1.3 秒，会超过 1.2 秒的目标。本轮 git 很快，慢服务端时 p95 是 1.09–1.10 秒。
4. **不可达只测了「连接被拒」。** 本容器的出站 TCP 会被透明代理接住，模拟不出丢 SYN、一直挂着的情况。不过：
   - 「连上之后不回应」已经由慢 3s 覆盖；
   - SessionStart 的 HTTP 有 1 秒硬上限；
   - Stop、SessionEnd、UserPromptSubmit 都不联网。
