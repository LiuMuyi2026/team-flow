# S1 同一个 `/mcp/` 服务两代协议（Claude Code 部分）

结论：**通过（Claude Code 部分）**。Codex 的两种方式（默认、`-c features.mcp_2026_07_28=true`）本机没有 Codex，**无法在此验证**，见文末补测步骤。

| 项 | 结果 |
|---|---|
| 默认设置 | 协商到 **2026-07-28**（新代：server/discover，无 initialize），list 9 个工具、call 成功 |
| `MCP_PROTOCOL_NEGOTIATION=legacy` | 协商到 **2025-11-25**（旧代：initialize），list、call 成功 |
| `MCP_SDK_GENERATION=v1` | v1 运行时，协商到 **2025-11-25**，list、call 成功 |
| 不带尾斜杠的 `/mcp` | 服务端内部改写，**没有 3xx**，全部 200 |
| 审批 | 配了 `--allowedTools "mcp__teamflow__*"`：读工具和写工具（claim_task）都**没被拒**；不配则被拒（annotations 不能代替 allow 规则） |
| `_meta` | 能看到。tools/call 带 `claudecode/toolUseId`、`progressToken`；新代另带 protocolVersion、clientInfo、clientCapabilities |
| structuredContent | **成功结果：模型只看到 structuredContent 的 JSON，看不到 content 文本**；**isError 结果：模型只看到 content 文本，看不到 structuredContent** |
| 3xx | 所有运行的服务端日志里都没有 3xx |

## 环境

- Claude Code 2.1.287（`claude --version`），服务端 FastMCP 4.0.10 + mcp 2.2.0，uvicorn 跑在 127.0.0.1:8191，`TEAMFLOW_LOG=/home/user/team-flow/spike/out/s1.log.jsonl`。
- 嵌套运行可用：`timeout 120 claude -p "只回复 OK" --max-turns 1` 回 `OK`，用时 4.1 秒。不需要降级为协议层模拟。
- 默认运行时由 feature flag 决定，本机调试日志是 `mcp runtime arm: v2 (source: growthbook)`；bare 模式下是 `v2 (source: default)`。成员电脑可能拿到别的 flag，需要补测。
- 嵌套会话的默认模型是 claude-sonnet-5-5，UA 是 `claude-code/2.1.287 (remote_mobile)`。`remote_mobile` 来自容器继承的 `CLAUDE_CODE_ENTRYPOINT`，成员电脑上会不一样。

## 结论与发现

1. **S1 的 Claude Code 部分通过。** 三种方式都能 list 和 call，不审批，没有 3xx，能看到 `_meta`。
2. **服务端报告不确定项 4 的答案**：Claude Code 不会把 content 和 structuredContent 都交给模型，**成功时只给 structuredContent**，不存在 token 重复。Codex 的行为另测。
3. **新问题（只报告，没改）：isError 时模型看不到错误码。** `_err()` 把错误码放在 structuredContent，content 只有中文 msg，所以模型看不到 `needs_human`、`needs_accept`、`taken`。
   - server instructions（plan 6.3）写的是"遇到 withheld、needs_human、needs_accept 时……"，模型拿不到这几个词。`withheld` 不受影响，它在成功结果里。
   - 目前每条 msg 都自带"已发到您的微信，请在手机上点……"，实测模型能照着做，行为上问题不大。
   - 建议二选一，并写进 plan 6.2 的"返回规范"：msg 以错误码开头，例如 `needs_human：T-51 是 bob 发布的……`；或者 instructions 改为按文字指引行事。
4. **alwaysLoad 生效。** inbox 直接调用；list_tasks 和 claim_task 先经过 ToolSearch（`select:mcp__teamflow__list_tasks`）再调用。本机开着 tool search，"9 个工具全量常驻"的预算算法只适用于关掉 tool search 的情况。
5. **每次连接多出 prompts/list、resources/list 两个请求。** 原因是 FastMCP 默认宣告了 prompts 和 resources 能力（服务端报告已提到）。影响很小，M1 可以关掉。
6. **测试提示词要避开"逐字复述上下文"。** S6 第一次用"请先逐字复述你上下文里以【teamflow 开头的那段"，被模型安全策略拦下：`model_refusal_no_fallback`、`api_refusal_category: reasoning_extraction`。改成提问式（"根据会话开始时看板提供的数据回答：我是谁、进行中的任务"）就正常。`doctor --live` 的提示词要按提问式写。
7. 验证中没有改任何代码。
