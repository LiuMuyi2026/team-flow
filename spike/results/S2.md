## Codex 部分（协议层模拟，本机没有 Codex）

依据的是 `$SP/codex`（openai/codex b707714，2026-10-01）：

## 发现

1. **哨兵必须用全角 `【teamflow`**：用旧的 `[teamflow` 时，Codex 会判 Failed、不注入，模拟结果与 CLI 报告一致。plan 6.1 和 6.6 的决策记录还需要同步修改。
2. **profile 有输出的危害比 plan 里说的大**：
   - plan 只提到「Codex 可能混入 profile 的输出」。实际上一旦走到 `$SHELL -lc` 这条退回路径，Stop hook 会**每一轮**都被 Codex 判为 Failed，UserPromptSubmit 每一轮都会注入 profile 的输出，SessionStart 的哨兵也不在首行了。
   - 正常路径是会话 shell 加 `-c`，不读登录 profile，所以不受影响。
   - 这时 doctor 必须把 `-lc` 也当作硬失败来报，目前已经是这样。
   - 修复提示里写的是 `[[ $- == *i* ]]`，那是 bash/zsh 的写法；`/etc/profile.d` 下的 sh 脚本要写成 `case $- in *i*) … ;; esac`。这个没改，只在这里记一笔。
3. **升级后是否仍是 Trusted，取决于组的位置**：
   - Codex 的信任状态存在 `config.toml` 的 `[hooks.state."<hooks.json 路径>:<事件>:<组序号>:<handler 序号>"].trusted_hash` 里（`hooks/src/lib.rs:113` 的 `hook_key`）。哈希只算事件名、matcher 和 handler 配置（命令串、timeout 等）（`engine/discovery.rs` 的 `hook_hash`），**键里却带着组序号**。
   - 所以升级 CLI 时，只要 `~/.local/bin/teamflow` 的路径不变，命令串和哈希就不变，仍是 Trusted。
   - 但 `teamflow setup` 的 `_append_groups` 会先删掉已有的 teamflow 组，再追加到数组末尾。如果用户或别的工具在我们后面又加了组，重跑 setup 会让我们的组序号变大，信任丢失。被挪到前面的那个组序号变了，它的信任也会丢。
   - 建议：setup 发现已有 teamflow 组时原地替换、不挪位置，只有没有时才追加到末尾。这改的是 plan 6.4「追加在末尾」的语义，所以只报告，没改代码。
4. **Codex 的 compact**：压缩完成后，`queue_pending_session_start_source(Compact)`（`core/src/session/mod.rs:4114`）把这次 SessionStart 排进队列，`run_pending_session_start_hooks` 到下一回合开始时才执行。因此压缩之后注入不是立刻出现，要等用户发出下一条消息。子 agent（ThreadSpawn）触发的是 SubagentStart，不是 SessionStart，我们没有注册这个事件，所以子 agent 不会收到注入。符合 plan 的意图。
5. **Codex hook 的 session_id**：`SessionStartRequest.session_id = sess.session_id()`，也就是根会话的身份（`agent_control.identity()`）。`codex exec` 的 `thread.started.thread_id` 是否就等于它，源码里看不出来，由 `codex_check.sh` 实测比对。
6. 当前的 Claude 配置下，Claude Code 的 hook 在 `-p` 模式下 4 个事件都会运行。SessionEnd 在 `result` 之后才运行，stream-json 里看不到它的事件，但会话文件里有 `ended`，服务端也收到了 end。
