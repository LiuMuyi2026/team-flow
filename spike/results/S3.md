# S3 Claude Code 的 headersHelper 能否拿到 `CLAUDE_CODE_SESSION_ID`

结论：**不通过**，已按 plan 11.2 的退路处理。

- headersHelper 拿不到它所属会话自己的 ID。
- **Claude 端已改为不发会话头**：`teamflow mcp-headers` 对 `--client claude` 和 `--client codex` 都不再发 `X-Teamflow-Session`。
- **Claude Code 的 MCP 调用一律归属到成员级**："alice 的 Claude Code"，不精确到会话。
- hooks 仍然按 hook 输入里的 `session_id` 精确登记会话。SessionStart、Stop、SessionEnd 走 `/api/v1/hooks/*`，不受影响。
- 服务端另加一层保险：`Service.resolve_session` 要求会话存在、未结束、`token_id` 和 `client` 都与当前 token 一致。不满足就降为成员级并写审计。

修复后复测（2026-10-02，端口 8194）：嵌套 `claude -p` 故意继承了外层会话 ID。所有 `/mcp/` 请求都没有会话头，只有 `hooks/session-start` 带会话 ID，值就是嵌套会话自己的。见 [evidence/S3_after_fix_e2e.txt](evidence/S3_after_fix_e2e.txt)。

后续（不改变上面的结论）：2026-10-02 用户拍板 D40，Claude Code 加第 5 个 hook PostToolUse，回合结束后把成员级的 MCP 调用补成会话级。真实 Claude Code 端到端的结果见下方「采用 PostToolUse 映射后的结果」。

## 做了什么

**修复前的实测**（2026-10-02 上午，Claude Code 2.1.287，端口 8191）：

1. headersHelper 包一层脚本 `spike/cc_probe/helper_wrap.sh`。它只记录会话相关的环境变量（不记录 token），然后 `exec teamflow mcp-headers`。
2. 用 `--settings` 配一个 SessionStart command hook（`spike/cc_probe/hook_record.py`），记录 stdin 的 `session_id` 和环境里的 `CLAUDE_CODE_SESSION_ID`。
3. 用 `--session-id <固定 uuid>` 给嵌套会话一个能认出来的 ID。外层容器自己的 ID 是 `1a6941c0-…`，会被嵌套进程继承。
4. 分三种情形：
   - **继承**：保留外层环境，模拟在 Claude Code 的 Bash 工具里再跑 `claude -p`；
   - **顶层**：`env -u CLAUDE_CODE_SESSION_ID -u CLAUDECODE -u CLAUDE_CODE_CHILD_SESSION`，模拟成员在自己终端里启动；
   - **随机 ID**：不指定 `--session-id`。
5. 对照组：
   - stdio MCP 进程能看到什么；
   - `tools/call` 的 `_meta` 里有什么；
   - PostToolUse hook 的 stdin 里有什么。

**修复后的复测**（2026-10-02 12:28，端口 8194，用独立 venv 里非 editable 安装的 teamflow）：

- `teamflow setup --home <临时目录> --clients claude` 写好用户级 settings。
- `claude -p` 的 hooks 和 allow 规则读临时 HOME 的用户级配置。
- MCP 用 setup 生成的 `claude-mcp.json`，加 `--strict-mcp-config`。
- 环境用 `env -i` 白名单，**故意保留外层的 `CLAUDE_CODE_SESSION_ID`**。
- 脚本见 [evidence/E2E_run1.txt](evidence/E2E_run1.txt) 的文件头。

## 结论

1. **S3 不通过。** Claude Code 2.1.287 只给 hook、Bash 和 stdio MCP 子进程设置 `CLAUDE_CODE_SESSION_ID`，headersHelper 用的是父进程原样的环境。
   - **顶层会话**：helper 里没有这个变量。
   - **嵌套会话**：在 Claude Code 的 Bash 工具里跑 `claude -p`、脚本或 workflow，helper 拿到的是**父会话的 ID**。
     - 父会话如果也是本人用同一个 token 登记的，服务端没法分辨。
     - 修复前，这种调用会被精确地记到父会话上。
   - 即使将来 helper 能拿到 ID，它也只在连接时运行一次，`/clear` 换了会话 ID 之后头不会更新。
2. **已执行退路：Claude 端 MCP 调用只到成员级。**
   - CLI：`cli/src/teamflow/headers.py` 不再发会话头，测试为 `test_cli_headers.py::test_never_sends_session_header[claude|codex]`。
   - 服务端：`resolve_session` 校验会话归属，测试在 `server/tests/test_sessions.py`。
   - plan 6.1「MCP 调用归属」一行、6.5 的归属表、D04 都要同步改，见 `docs/m0.md`「对 plan 的修订建议」。
3. **可选方案（供决策，M0 不实现）：用 PostToolUse 把成员级调用补成会话级。**
   - **依据**：PostToolUse hook 输入里的 `tool_use_id` 等于同一次调用 `_meta["claudecode/toolUseId"]` 的值。
   - **做法**：
     - 加第 5 个 hook：PostToolUse，matcher 写 `mcp__teamflow__.*`；
     - hook 只往 spool 写 `(session_id, tool_use_id)`，不联网，不读 `tool_input`、`tool_response`（按 plan 6.4 规则 5，这两项是正文，不能上传）；
     - 服务端按 `_meta["claudecode/toolUseId"]` 把成员级调用补成 exact。
   - **代价**：
     - 多一条冻结后不能改的命令串；
     - 每次 MCP 调用多一次 hook 冷启动（约 20ms，在 S4 的 UserPromptSubmit 量级）；
     - `claudecode/` 是未文档化的键，会随版本变化。
   - **必须在冻结命令串之前决定**：之后再加，Codex 不受影响，但 Claude Code 的 settings 要全员重跑 setup。
   - 另一条路是把 teamflow 做成本地 stdio 中转，stdio 进程能拿到正确的 ID。架构改动大，不建议。

## 采用 PostToolUse 映射后的结果（D40，2026-10-02，端口 8198）

S3 的结论不变：headersHelper 拿不到本会话的 ID，调用**到达时**仍是成员级。D40 拍板后，按结论第 3 条的可选方案实现了 PostToolUse 映射，本节是验证阶段的结果。

**实现**（plan 6.4、6.5、5.1；`server/README.md`「Claude Code 的 PostToolUse 映射」）：
- setup 给 Claude Code 写第 5 个 hook：`{"matcher": "^mcp__teamflow__.*", "hooks": [{"type": "command", "command": <bin>, "args": ["hook", "tool", "--client", "claude", "--cred", <abs>], "timeout": 2}]}`，同步执行，不设 `async`。Codex 仍是 4 个。
- hook 从输入里取 `session_id`、`tool_use_id`、`tool_name`，往 spool 写 `{"type":"tool_map","key":hash(client,session,tool_use_id),"session_id","tool_use_id","tool"}`；不读 `tool_input`、`tool_response`，不联网、不拉起进程、不输出。
- Stop 拉起的 flush 经 `POST /api/v1/hooks/batch` 上报。服务端按 (token, tool_use_id) 对上 tools/call 记下的 `_meta["claudecode/toolUseId"]`，会话过 `resolve_session`，把这次调用的成员级事件补成 exact；认领、开始类事件顺带设置会话的 current_task。

**真实 Claude Code 端到端**（claude 2.1.287，独立 venv 非 editable 安装的 teamflow，`teamflow setup --home <临时目录>`，嵌套 `claude -p` 调 inbox 和 `claim_task(T-53)`，故意保留外层的 `CLAUDE_CODE_SESSION_ID`；[evidence/S3_posttooluse_e2e.txt](evidence/S3_posttooluse_e2e.txt)）：

| 运行 | 协议 | PostToolUse | tool_use_id 与 `_meta` | claim_task 的事件 | Stop 后、SessionEnd 前 | 会话结束后 |
|---|---|---|---|---|---|---|
| default | 2026-07-28（modern） | inbox、claim_task 各一次，exit 0，无输出；ToolSearch 不触发 | 两次调用都相等 | task.claimed、task.started：member → **exact**，`actor_session_id` = SessionStart 登记的 `e2ed0001-…`，`session_src=tool_map` | 会话 current_task = T-53；bob 的 `/status` 看到 alice `sess=[{claude_code, e2ed0001, T-53}]` | 事件仍 exact；current_task 随 end 清空 |
| v1（`MCP_SDK_GENERATION=v1`） | 2025-11-25（legacy） | 同上 | 两次调用都相等 | 同上，会话 `e2ed0002-…` | current_task = T-53 | 同上 |
| plain（不加观察 hook） | 2026-07-28 | 同上 | 两次调用都相等 | 同上，会话 `e2ed0003-…` | Stop 的 flush 先于 end 送达，current_task 设过（`current_task_ev=17`） | 同上 |

- inbox 是读工具，不产生事件，没有可补的；它的映射服务端确认收下、不存。
- 三次的 spool 都是 4 条已上报（turn_end、end、两条 tool_map），dead-letter 0；doctor 的 5 个 hook 全部通过。
- 事件挂到的是嵌套会话自己的 ID，不是继承来的外层 `1a6941c0-…`：PostToolUse 的 `session_id` 来自 hook 输入。

**对抗**（真实服务端，27 项全过；另对 `hook tool` 做了 25 项异常输入，全部 exit 0、无输出、strace 里没有 connect 和 fork）：
- B 的 Claude Code token 用 A 那次调用的 tool_use_id 上报：映射按 B 的 token 存，A 的事件不变（n=0）；指向 A 的会话：403 ignored，审计 `session.resolve token_mismatch source=tool_map`；B 先拿 A 的会话 ID 做 session-start 也抢不走会话；B 的 Codex token、A 的 Codex token 上报：403 ignored(client)。
- B 在自己的 tools/call 里伪造同一个 `claudecode/toolUseId`：只挂到 B 自己的会话；A 的 Claude Code token 映射不到 A 的 Codex token 的事件。
- 14 种非法 tool_use_id（含结尾换行、全角、超长、非字符串）、9 种非 teamflow 工具名：全部 422 bad；`_meta` 里非法的 toolUseId 不记到事件上。
- 重复：同 key 同批或跨批都是 409 dup；换 key 同会话 n=0；同一 tool_use_id 改指本人另一个会话 403 conflict，先到的为准；已经 exact 的事件不被改写；指向上一批已结束的会话、不存在的会话：403 ignored。

**验证中发现并修掉的问题**：
- **spool 跨批的先后**：Stop 那一轮上报失败、tool_map 进了退避，服务端恢复后 SessionEnd 的 `end` 会先单独送到，服务端再把迟到的 tool_map 判成"会话已结束"（403），映射丢了还进 dead-letter，doctor 报失败。用真实服务端复现过（事件一直是 member，dead-letter 1）。改为同一会话按写入顺序上报：更早的记录还在退避时，同会话后写的等它到期一起发（`cli/src/teamflow/spool.py` 的 `_due`，`cli/tests/test_cli_spool.py` 新增 4 个用例）；修复后同一复现脚本：三条同批送达、事件 exact、dead-letter 0。
- 服务端几处 `^…$` 配 `.match` 的校验（标识、提交 SHA、结束原因、handle）会放过结尾的换行，改成整串匹配（`server/tests/test_sanitize.py::test_anchored_checks_reject_trailing_newline`）。

**仍然覆盖不到、留在成员级的**：工具返回 isError（Claude Code 触发 PostToolUseFailure，不装）；bare 模式（没有 hook）；回合结束、映射送达之前；`claudecode/toolUseId` 是未文档化的键，改版后失效时整体退回成员级（plan 6.8 失败降级）。
