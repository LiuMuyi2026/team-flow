# S3 Claude Code 的 headersHelper 能否拿到 `CLAUDE_CODE_SESSION_ID`

结论：**不通过**。headersHelper 拿不到它所属会话自己的 ID。按 plan 11.2 的退路，MCP 调用归属到成员级。

还有一个比"拿不到"更要紧的问题：嵌套运行时，helper 拿到的是**父进程继承来的别的会话 ID**。CLI 现在会把它当作 `X-Teamflow-Session` 发出去，会话会归属错。

## 做了什么

1. headersHelper 包一层脚本（通用版是 `spike/cc_probe/helper_wrap.sh`），只记录会话相关的环境变量（不记录 token），然后 `exec teamflow mcp-headers`。
2. 用 `--settings` 配一个 SessionStart command hook（exec form，通用版是 `spike/cc_probe/hook_record.py`），记录 stdin 的 `session_id` 和环境里的 `CLAUDE_CODE_SESSION_ID`。
3. 用 `--session-id <固定 uuid>` 给嵌套会话一个能认出来的 ID。外层容器自己的 ID 是 `1a6941c0-21de-5c92-8067-c298f2345b24`，会被嵌套进程继承。
4. 分三种情形：
   - **继承**：保留外层环境变量，模拟"在 Claude Code 的 Bash 工具里再跑 claude -p"；
   - **顶层**：`env -u CLAUDE_CODE_SESSION_ID -u CLAUDECODE -u CLAUDE_CODE_CHILD_SESSION`，模拟成员在自己终端里直接启动；
   - **随机 ID**：不指定 `--session-id`。
5. 对照组：同一会话里的 stdio MCP 进程能看到什么；`tools/call` 的 `_meta` 里有什么；PostToolUse hook 的 stdin 里有什么。

命令（与 S1 相同的隔离方式，见 S1.md）：

```bash
# 继承
run_nested.sh s1_default 11111111-1111-4111-8111-111111111111 "$P" -- --settings settings_s1.json --mcp-config mcp_s1.json --strict-mcp-config --allowedTools "mcp__teamflow__*"
# 顶层
env -u CLAUDE_CODE_SESSION_ID -u CLAUDECODE -u CLAUDE_CODE_CHILD_SESSION \
  run_nested.sh s3_toplevel 88888888-8888-4888-8888-888888888888 "$P" -- （同上）
# 随机 ID
run_nested.sh s3_inherit_randomsid - "$P" -- （同上）
```

## 原始输出摘录

`hh_env.jsonl`（helper 看到的）和 `hook_record.jsonl`（SessionStart hook 看到的）对照。`X-Teamflow-Session` 取自服务端日志的 `sess` 字段：

| 运行 | hook 的 stdin.session_id | hook 环境里的 `CLAUDE_CODE_SESSION_ID` | **helper 环境里的 `CLAUDE_CODE_SESSION_ID`** | 服务端收到的 `X-Teamflow-Session` |
|---|---|---|---|---|
| s1_default（继承，v2） | 11111111-… | 11111111-… | **1a6941c0-…（外层的）** | 1a6941c0-… |
| s1_legacy（继承，legacy） | 22222222-… | 22222222-… | **1a6941c0-…** | 1a6941c0-… |
| s1_v1（继承，v1 运行时） | 33333333-… | 33333333-… | **1a6941c0-…** | 1a6941c0-… |
| s3_inherit_randomsid（继承，随机 ID） | b277b359-… | b277b359-… | **1a6941c0-…** | 1a6941c0-… |
| s3_toplevel（顶层） | 88888888-… | 88888888-… | **None** | 没有这个头 |

`s3_toplevel` 调试日志里 helper 产出的头（原文）：
```
"headers":{"User-Agent":"claude-code/2.1.287 (remote_mobile)","Accept-Encoding":"identity","Authorization":"[REDACTED]","X-Teamflow-Client":"[REDACTED]"}
```

helper 能拿到的只有文档列出的那几个：`CLAUDE_CODE_MCP_SERVER_NAME=teamflow`、`CLAUDE_CODE_MCP_SERVER_URL=http://127.0.0.1:8191/mcp/`；其余是父进程原样的环境。每次会话只运行一次 helper，就在连接时（调试日志 `Executing headersHelper to get dynamic headers` 每次运行出现 1 次）。

CLI 自己的调试日志（`TEAMFLOW_DEBUG=1`）只记录"有没有拿到"。继承的情形下它照样记成 yes，**没法分辨是不是自己的会话**：
```
2026-10-02T03:06:24 pid=8455 mcp-headers client=claude session_env=yes   ← s1_default，实际是外层 ID
2026-10-02T03:10:02 pid=9581 mcp-headers client=claude session_env=no    ← s3_toplevel
```

### 对照：哪些地方能拿到正确的会话 ID

**stdio MCP 进程**（探针 `echo_env`）：嵌套和顶层两种情形都拿到了自己的 ID。
```
s3_stdio_env      → {"CLAUDE_CODE_SESSION_ID":"eeeeeeee-0000-4000-8000-000000000001","CLAUDECODE":"1"}
s3_stdio_env_top  → {"CLAUDE_CODE_SESSION_ID":"eeeeeeee-0000-4000-8000-000000000002","CLAUDECODE":"1"}
```
按 cc_envvars.md 365 行，stdio 进程保留的是它启动时的 ID，`/clear` 之后不会更新。

**`_meta["claudecode/toolUseId"]` 等于 PostToolUse hook 的 `tool_use_id`**。探针 `echo_meta` 回显的 `_meta`，与 `--settings` 里 PostToolUse 记录 hook 的 stdin 对照：
```
[v2 运行时，新代] _meta = {'io.modelcontextprotocol/protocolVersion': '2026-07-28', 'io.modelcontextprotocol/clientInfo': {...'claude-code'...'2.1.287'...},
                          'io.modelcontextprotocol/clientCapabilities': {...}, 'claudecode/toolUseId': 'toolu_012HDfH2mEGmyGFoKMDw5GJw', 'progressToken': 3}
  PostToolUse stdin: session_id=99999999-9999-4999-8999-999999999990  tool_use_id=toolu_012HDfH2mEGmyGFoKMDw5GJw  tool_name=mcp__probe__echo_meta
[v1 运行时]      _meta = {'claudecode/toolUseId': 'toolu_018mtaXS32pXAsBn1eDV31wG', 'progressToken': 4}
  PostToolUse stdin: session_id=99999999-9999-4999-8999-999999999991  tool_use_id=toolu_018mtaXS32pXAsBn1eDV31wG
```
teamflow 自己的服务端日志里，两代协议的 tools/call 都有 `claudecode/toolUseId` 这个键（见 S1.md）。

PostToolUse 的 stdin 键：`cwd, duration_ms, effort, hook_event_name, mcp_server, permission_mode, prompt_id, scratchpad_dir, session_id, tool_input, tool_name, tool_response, tool_use_id, transcript_path`。其中 `tool_input` 和 `tool_response` 是正文，按 plan 6.4 规则 5 不能上传。

## 结论

1. **S3 不通过。**
   - 这个版本（2.1.287）的 Claude Code 只给 hook、Bash 和 stdio MCP 子进程设置 `CLAUDE_CODE_SESSION_ID`，**headersHelper 不设**，用的是父进程原样的环境。
   - 顶层会话：helper 里没有这个变量，CLI 不发头，退回成员级。结果正确，只是精度低。
   - 嵌套会话：成员在 Claude Code 的 Bash 工具里跑 `claude -p`、跑脚本或 workflow 都属于这种。helper 继承了**父会话的 ID**，CLI 会把它当作 `X-Teamflow-Session` 发出去。父会话也是本人用同一个 token 登记的，服务端的"属于本人"校验会通过，于是**子会话的 MCP 调用被精确地记到父会话上**。
   - 即使将来 helper 能拿到 ID：helper 只在连接时运行一次，`/clear` 换了会话 ID 之后头也不会更新。
2. **建议（只报告，没改）：`teamflow mcp-headers --client claude` 不再发 `X-Teamflow-Session`。** 涉及 `cli/src/teamflow/headers.py` 的 `SESSION_ENV`，以及 `cli/tests/test_cli_headers.py::test_session_header_from_env` 的 claude 用例。
   - 没有直接改的原因：plan 6.5 写的是"S3 验证通过才用请求头"，这属于设计决策。按 AGENTS.md，要先改 plan 6.1、6.5 的决策记录。
   - 服务端也可以对 `claude_code` 客户端忽略这个头，作为双保险。
   - Codex 不受影响：Codex 运行 helper 前会清空环境，拿不到 `CODEX_SESSION_ID`，本来就发不出这个头。
3. **新发现的可选方案（供决策，不在 M0 实现）：用 `claudecode/toolUseId` 关联会话。**
   - 做法：第 5 个 hook，PostToolUse，matcher 写 `mcp__teamflow__.*`。只往 spool 写 `(session_id, tool_use_id)`，不联网，不读 `tool_input`、`tool_response`。服务端按 `_meta["claudecode/toolUseId"]` 把成员级调用补成 exact。
   - 代价：多一条冻结后不能改的命令串；`claudecode/` 前缀是未文档化的键，会随版本变化。要做，就必须在冻结命令串之前定下来。
   - 另一条路是把 teamflow 做成本地 stdio 中转（stdio 进程能拿到正确 ID），对架构改动大，不建议。
4. 验证中没有改任何代码。

## 需要成员电脑补测

1. **交互式 TUI**（真实登录，非嵌套），只测 0.5 小时。
   - MCP 配置的 headersHelper 换成 `spike/cc_probe/helper_wrap.sh --client claude --cred <abs>`，启动前 `export TF_PROBE_OUT=/tmp/teamflow-probe`；hooks 加 `spike/cc_probe/hook_record.py`。
   - 启动 `claude`，问一句话，再 `/clear`，然后 `/mcp` 里 reconnect teamflow。
   - 对比 `/tmp/teamflow-probe/hh_env.jsonl` 和 `hook_record.jsonl`。期望 helper 一直是 None。如果某个版本开始给 helper 设置了会话 ID，要再确认 `/clear` 之后它会不会跟着更新。

3. 如果决定走第 3 条（PostToolUse 关联），在 macOS 和 Windows 上各确认一次 `_meta` 里有 `claudecode/toolUseId`，且与 PostToolUse 的 `tool_use_id` 相等。
