# 邻桌 / Longtable 新方向评估：开源免费、本地化、可视化、可连接性与合作方案

日期：2026-10-03 · 状态：方向评估（已按三方红队意见修订），等你拍板。本文**不改** `docs/plan.md`；拍板后再把结论写进它的决策记录（第 13 节） · 读者：要拍板的人、要实现的人

**起因**：用户 2026-10-03 定了四个新方向：
1. 以后开源、免费；
2. 能不能本地化、不用（我们的）服务器，确保用户数据安全；
3. 可视化和 UI 要优于别的产品；
4. 可连接性（能接的 agent、工单、聊天工具、协议）要优于它们。

## 0. 一页结论

> 本版已按安全、可行性、市场三个视角的红队意见修订（2026-10-03）。主要变化有四处：
> 1. 节奏改为"试点先行"：先在香港机上用 C′ 给 owner 团队试点，11 月中旬判断产品论点，再做路线 B；
> 2. 安全口径收紧：手机网页当确认设备时，中继的运维方仍在信任范围内；电脑浏览器里不放能静默使用的解密钥匙；
> 3. 工期改报 P50 和区间，补上原来漏算的守护进程、安全发布和 L2 的几项；
> 4. "优于对手"改成同场可测的口径。

### 0.1 四个方向：能不能做、推荐怎么做、代价是什么

| 方向 | 能不能做 | 推荐怎么做 | 代价与前提 |
|---|---|---|---|
| ① 开源、免费 | 能。但这只是入场门票：Paperclip（MIT）已开源，Multica 可以自托管（许可证不是 OSI 开源），两者都能在自己的机器上跑、不要出品方账号。在这一条上我们与 Paperclip 持平，只在许可证上比 Multica 更开放 | 全部代码和协议规范用 Apache-2.0，文档用 CC-BY-4.0；贡献走 DCO，不签 CLA；名字靠商标政策管。项目不运营任何存放团队数据的服务器 | 没有收入，最大的成本是维护者时间；调研报告建议的按人收费作废。准确说法是"软件免费"：跨境团队通常还要约 ¥115/月的中继和一个域名（通行密钥不认 IP）。GitHub Sponsors 不支持在中国大陆收款 |
| ② 本地化、不用服务器、数据安全 | **能做到**：不用**我们的**服务器（与对手的自托管版持平）。路线 B 还额外做到三点：每台设备有完整副本，离线能读能签；中继只存密文，磁盘、备份、快照泄露，或云厂商查看存储，都读不到正文；承诺由本人的人类密钥签名，每个客户端都验签，agent、连接器、中继都伪造不了。**有前提**：手机网页（PWA）当确认设备时，能改中继上网页代码的人（中继 root、部署凭据持有人、域名和 DNS 账号、云厂商）仍能读到明文，也能诱导本人签下别的承诺，要有原生确认 app 才能把中继移出信任范围；在电脑浏览器里显示过的正文，同用户的 agent 能读到；被接受的正文按设计会经各人的 agent 发给模型厂商。**做不到**：一台常开的机器都没有。上海和洛杉矶 09:00–21:00 只重叠 3–4 小时，纯 P2P 下手机确认、按时通知、及时撤销都做不好 | 先用 C′ 在 owner 团队试点验证产品论点（见 0.3），通过后做路线 B 作开源首发：签名并端到端加密的事件日志，经团队自选、只存密文的中继同步；人类承诺就是人类密钥的签名；别人写的正文只封装给人类密钥（密码学闸门），电脑浏览器里不放能静默使用的解密钥匙（#28）；本机守护进程以独立系统用户运行，负责 10 分钟延迟和撤销。备选 C+：团队自托管服务端，承诺照样用人类密钥签名、客户端验签，但不做端到端加密，比 B 少约 6–8 周，服务器看得到明文 | B 的 L0 + L1 约 15–21 个工作周（P50 约 18），比 C+ 多 6–8 周。安装要一次管理员授权，走签名的系统安装包；WSL 开着 interop、在 docker 组里或有免密 sudo 的电脑，自动降为同用户模式。中继看得到元数据，开了 notifier 还看得到谁在什么时候收到哪类通知。已经同步出去的历史，撤销也收不回 |
| ③ 可视化和 UI 优于对手 | 能做出对手没有的视图；"优于"按什么算，要你定（#23） | 首发三个视图：谁在等谁、接力、我的 agent 能看到什么；Claude Code 状态栏和页脚链接。用同一份种子场景，和 Paperclip 本地版、Multica 自托管版同场比答题的速度和正确率；第一轮在 C′ 试点里用视图 1 跑 | 三个视图约 18–22 人日。对手的界面本次只读了文档和 README，没有同场实测。秒开、离线可读不是我们独有的（Linear 已做到，Multica 有桌面版和 iPhone 版），B 独有的只有离线确认。要守住规划 7.4「不监控人」；中英双语约 1–1.5 周，之后文案维护量翻倍 |
| ④ 可连接性优于对手 | 能。比的是接得深、接得对、中美两地都接得到，不比"能拉起几种 CLI" | 一个 hook 入口 + 一张数据化的 agent 适配表；首发时 5 家 CLI 接到 L3 以上。每周跑静态兼容性 CI，每次发版在两地机器上手动跑 live 检查。人的通知用 Apprise，每人自选渠道；工单只同步元数据，不需要公网 IP；MCP、Agent Skills、AGENTS.md 必做。连接器签不出承诺，第三方连接器强制沙箱 | 连接相关约 50 人日。对外只说不依赖"对手还没做"的性质：基线是 Multica v0.6.1（2026-10-01），首发前要按对手最新版重测。hooks 自动接入在单人工具里已有先例（Emdash、Warp），"团队协作产品里只有我们做"随时可能失效。适配表和 CI 结果是公开的公共层，对手也能用，不是护城河。飞书、钉钉、企业微信要你重新表态 |

### 0.2 推荐的合作方案组合

- **主体自己做**：独立实现，不 fork、不并入任何项目。
  - 复用 M0 约 80% 的设计。选 TS 内核后，代码能复用的只有 CLI 的 hook 路径和网页组件，约占 M0 的 40%；内核代码复用为 0，约一半内核规则要新写（6.3）。
  - D01 写的重新评估条件是"出现许可证友好的同类开源项目"，Paperclip（MIT）已经触发了这一条。评估后结论仍是自建：Paperclip 是中心服务，心智是替用户跑 agent；它的插件规范明令插件不能改审批和 checkout，"承诺只归人"和接受闸门都做不进去。
- **直接依赖的库**：Apprise（BSD-2，出站通知）、WebCrypto、@simplewebauthn、MCP 官方 SDK。
- **只借设计，不拷代码**：

  | 项目 | 借什么 |
  |---|---|
  | git-bug（GPL-3.0） | 实体 DAG 和确定排序 |
  | Keyhive（pre-alpha） | 威胁模型和撤销规则 |
  | secsync | 快照 + 更新的结构 |
  | @localfirst/auth | 邀请和签名链 |
  | p2panda-auth | strong removal |
  | Paperclip | 能力声明 |
  | Buzz | 动态流原则 |
  | beads | 哈希 ID |

- **兼容**：只做导入导出或桥，永远不当事实来源。
  - beads、Backlog.md：L3，作为连接器 SDK 的示例；
  - GitHub、Gitee：L2 做 PR 关联，L4 做 issue 镜像；
  - 首发后第一批做一座桥当分发实验：推荐 c3 Multica 连接器（约 1 周，经它 MIT 许可的 CLI），配"8 周内经这座桥接入的团队数"指标；Paperclip 插件桥、"带人类确认的 AAMP"桥、ACP 启动器按需求信号再做。
- **对外输出**：把"人类承诺证明 + 接受闸门 + 外部内容信封 + 连接器清单"写成 Apache-2.0 开放规范，附一致性用例，L3 发布，第三方连接器和兼容实现都要用它。是否主动邀请对手实现，有条件地做（#22）：规范一旦被对手做成可选开关，我们剩下的差异见 5.6。
- **分发**：合作不承担首发分发。首发分发靠 5.5 的渠道、外部设计伙伴的试用报告，以及 Claude Code marketplace 和 MCP Registry 的条目。
- **不做**：
  - fork Paperclip，或把邻桌做成它的插件；
  - 向 Multica 贡献核心或并入 Multica：它的贡献条款允许出品方单方面改许可证，并把贡献用于云业务；
  - 用 Automerge、Yjs、Loro、Jazz、Keyhive、any-sync 作看板底座；
  - A2A；
  - 非 OSI 许可证；
  - 存放团队数据的官方公共中继；
  - 遥测。

### 0.5 最大的三个风险

1. **工期长，而且只有一个验证者**（R1、R32）。B 首发 P50 约 2027 年 8 月上旬，区间到 9 月中旬；一名开发者，安全关键代码都要 owner 审。对策：试点先行，11 月中旬先判断产品论点；B 和 C+ 在判决时再选一次；落后按 7.4 的顺序砍；L2 期间引入外部设计伙伴。
2. **安全说法超出实际**（R4、R5、R7、R15）。PWA 当确认设备时，中继的运维方能读明文、诱签承诺；电脑浏览器里存着的解密钥匙，同用户 agent 能静默使用；隔离守护进程在 WSL interop、docker 组、免密 sudo 下能被绕过。这些一旦被安全社区先指出，"数据安全"的定位就毁了。对策：按 #1 收紧口径；电脑上不放能静默使用的解密钥匙（#28）；doctor 自动降级；中继管理凭据只用硬件密钥；L0 闸门和一致性用例覆盖对应的攻击；首发前尽量做外部评审（#27）。
3. **差异化守不住**（R13、R30）。开源、自托管只是和对手持平；适配表和兼容性结果是公开的；对手可以把闸门做成默认关闭的开关，不必拆自己的卖点。对策：对外只说不依赖"对手还没做"的性质；首发前按对手最新版重测；同场比较 UI；开放规范的邀请有条件地发（#22）；用外部团队的真实使用数据说话。

## 1. 本地化、不用服务器

### 1.1 先把"不用服务器"说准

| 口径 | 含义 | 能不能做到 | 说明 |
|---|---|---|---|
| ① 不用**我们的**服务器 | 项目不运营任何存放团队数据、或替团队做授权判断的机器 | 能 | 项目只发布软件和规范。Multica 自托管版、Paperclip 本地版也做到了，这一条与对手持平 |

读法：
- 自托管这一条是持平（许可证上我们比 Multica 更开放，和 Paperclip 一样）。B 真正多出来的只有"中继看不到明文"和"离线确认"；C+ 已经能做到"伪造不了承诺、注入不了 agent"。
- 对 2–5 人团队，服务器管理员通常就是队友。"中继看不到明文"主要防的是云厂商、备份和快照泄露、香港机被入侵后的被动读取；以后有原生确认 app，才也能防主动攻击。
- 这一点值不值 6–8 周，列为 C′ 试点访谈的必答题："中继看不到明文，会不会改变你在我们和 Multica 自托管之间的选择？"答案进 #2 的拍板。

**为什么首发推荐 B，又为什么先做 C′**：
- C 最快，但明文仍放在一台服务器上，这台服务器仍是全体 agent 的信任根；每个小团队还要自己运维一套完整服务。这和"本地化、数据安全"只对得上一半。
- C+ 补上了"伪造不了承诺、注入不了 agent"，但服务器仍看得到明文，也不能离线确认，不算"本地化"。它比 B 少 6–8 周，是 C′ 判决时的正式备选。
- B 是唯一真正"本地化"的路线：每台设备有完整副本，离线能签；"别人的文字要本人接受"从"相信服务器会执行"变成密码学闸门。代价见 0.1。
- 先做 C′ 不会让规则多写一遍。C′ 用 M0 的 Python 代码，用完即弃；B 本来就要按 TS 内核重写（#4）。C′ 里作废的是 Python 持久化层、REST、ceremony 表和部署脚本，约 1.5–2 周。能带进 B 的有：网页组件、视图 1 的派生函数（用 TS 写在网页侧）、notifier 模板和 D62 时区规则的设计，以及试点得出的结论。上一版写的"规则要写两遍、多 3–4 周"不成立，已删。
- 上一版说"中心化的对手要拆掉自己的架构才能跟进"，说过头了：对手可以把闸门做成默认关闭的开关，不必拆架构（5.6）。

| 事件日志 | 团队唯一的权威数据。外层信封明文：团队 ID、事件哈希、设备假名（按 epoch 换）、每设备序号和上一条的哈希、epoch、规则集版本。内层用团队 epoch 密钥做 AES-256-GCM 加密。每条事件附中继签的接收回执 {seq, 时间} | 不存会话细节（只在本人设备上） |
| 守护进程（每台电脑一个） | 同步、折叠、验签、执行本人的闸门和延迟；给 hook 写结构化缓存；对 agent 提供 stdio MCP（9 个工具不变） | 不持有任何人类密钥；不对本人的系统用户提供任何返回未接受正文的接口 |
| 网页 app（电脑浏览器、手机 PWA） | 人的界面；用人类密钥签承诺；确认设备上解正文；IndexedDB 里只存密文 | 不对 agent 开放；电脑浏览器不放能静默使用的解密钥匙（1.5.5） |

| 可选远端（L4） | git、S3 兼容对象存储、WebDAV、本地文件夹，作为备份和交叉校验 | 手机不连 |

### 1.4 中美时差下，异步同步怎么保证

4. 王电脑上的守护进程同步到这条事件，放行给王的 Codex，并删掉过期的放行私钥。
5. 赵第二天早上的"您不在的时候"里显示：王已接受（王当地 09:05）。

### 1.5 数据安全模型

#### 1.5.1 密钥

| 密钥 | 放在哪 | 谁能用 | 用来做什么 | 丢失或被盗时 |
|---|---|---|---|---|
| 确认设备密钥（confirm，人类） | 两类签名器，名册里登记类型：①手机 PWA：WebCrypto 不可导出的 P-256 设备密钥，**必须**和同一个摘要上 UV=1 的通行密钥断言一起出现才算人类签名；②原生 app：Android Keystore（`AUTH_BIOMETRIC_STRONG`，每次使用都验证）或 iOS Secure Enclave（`biometryCurrentSet`），由硬件强制每次人体动作，可以单独签 | 本人，必须有人体动作 | 签 T1 和 T2；解内容密钥 | 审批人在自己的确认设备上代签撤销（T2），然后换代；全部丢失走恢复流程 |
| 桌面人类密钥（desk，弱档） | 电脑浏览器里的通行密钥，用来签名。解密：默认只用 WebAuthn PRF 包裹的解密密钥，每次解封都要一次 UV，只在内存里用，绝不落盘；平台不支持 PRF 时不登记解密密钥（只签不解，#28） | 本人。同用户的 agent 能驱动浏览器（CDP、Claude in Chrome），能调用页面里任何不需要 UV 的密钥；通行密钥在 macOS Chrome 上能用登录口令满足 | 签 T1（延迟生效）；PRF 平台上在电脑上看正文 | 只能撤销 desk 自己；其余同上 |
| 节点密钥（agent 级） | 隔离守护进程，以独立系统用户运行 | 只有守护进程。agent 只能经 MCP 请它签 agent 级事件、取已放行的内容 | 签 agent 级事件 | 电脑丢了：确认设备签撤销，然后换代 |
| 放行密钥（按天轮换） | 隔离守护进程 | 只有守护进程 | 接受事件把内容密钥转封给它；到点放行时守护进程解开，转存进本机加密存储，再删掉当天的私钥 | 泄露只影响还没删掉的那几天，解不开更早转封过的内容 |
| 团队 epoch 密钥（对称） | 每台成员设备 | 全体成员设备 | 加密信封内层：状态、标识、团队档下的标题 | 移除成员或设备就换代 |
| 内容密钥（每版正文一把） | 封装给全体成员的确认设备密钥、登记了的 PRF 包裹 desk 解密密钥，以及作者本人的守护进程；接受后转封给接受人当天的放行密钥 | — | 加密正文、困难详情、人写的评论；严格档下标题也用它 | 抹除只能靠全体删除这把密钥，没法强制别人的设备删 |
| 纸质恢复密钥 | 纸上 | 本人 | 只能签"申请重新登记"，签不了任何承诺 | — |
| 连接器子密钥 | 守护进程持有（中继上的连接器用中继持有的一把）；启用时登记进名册（T2） | 只有守护进程；连接器只能请求签名，守护进程按清单的 emits 白名单代签 | 只能签外部观测、外部提议类事件 | 撤销 |
| 中继回执密钥 | 中继 | 中继 | 给每条事件签 {seq, 时间} 回执 | 换中继时由审批人签名册事件更换 |
| 项目发布密钥 | 离线，owner 的硬件密钥 | owner | 签发行版和网页包 | 走发布密钥轮换流程，写进 SECURITY.md |

密码学原语统一用 P-256：ECDSA 签名，ECDH + HKDF-SHA256 + AES-256-GCM 封装，JCS（RFC 8785）做规范化。理由是 WebAuthn 默认 ES256，WebCrypto 在所有平台都支持 P-256；各浏览器对 Ed25519/X25519 的支持版本不齐〔未核实〕，所以选最稳的。只组合标准原语，不自研协议。结构参考 secsync，威胁模型参考 Keyhive〔原文，高〕。

#### 1.5.2 中继看得到什么

**只开同步时**：看得到团队 ID、事件哈希、设备假名（按 epoch 换；连接时的挑战应答仍会把设备和连接对上）、每设备序号、epoch 号、密文大小、到达时间、来源 IP，以及由此看出的活动节律。看不到标题、正文、状态、指派关系。这和 Keyhive 威胁模型里"不可信中继能看到操作哈希、大小、时间和成员关系图"是同一级别〔原文 keyhive threat_model，高〕。

**开启各可选组件后**：

| 组件 | 中继额外看得到 | 推荐配置 |
|---|---|---|
| notifier（邮件、微信测试号、Bark、ntfy） | 收件人的 handle、联系方式、时区和假期；每条通知的枚举类别（如"指派""请您帮忙"）、哈希 ID、发送时间。由此能推出谁在什么时候被指派、被请求帮忙 | 默认开（#14）；发送方只给 {handle、类别、哈希 ID}，不给标题；这些数据写进律师问题（#10）和"数据去向"页 |
| 晨间摘要邮件 | 如果在中继上拼标题：全部标题和状态 | 只发"有 N 件在等您，打开 app 查看"；带标题的摘要由本人设备在打开 app 时生成 |
| 中继上的工单 webhook 连接器 | 外部平台推来的数据（本来就是外部的） | 只允许"收外部数据 → 封给成员密钥 → 用中继连接器子密钥签名"；清单里 `runs_on` 含 relay 时不许有 `reads` |
| 云端会话的 HTTP MCP、中继上的 IM 机器人（L4） | 要在中继上持有解密密钥：全部明文 | 单列"中继可解密"一档，开启算 T2，"数据去向"页醒目标出 |
| 网页包托管 | 无新增，但它下发的代码在 PWA 上运行 | 见 1.5.6 |

**元数据也要少给**。中继管理员通常就是 owner，正是规划 7.4「不监控人」要防的那一方，所以：
- 回合结束、工具映射、会话开始和结束、心跳只留在本机，不上传；
- agent 级事件按小时加抖动批量上传，事件里的时间取整到小时；"agent 已离线"由本人设备算好档位再同步；人的承诺和撤销照常立即上传；
- 中继默认不记访问日志，不长期保存到达时间和 IP；
- 拉取和订阅都要按名册里的设备密钥做挑战应答，邀请链接里的 team_id 不能单独用来下载日志；
- 告知书写明中继管理员能看到的活动节律；
- 不做流量填充。

#### 1.5.3 撤销和移除

- 停用设备或移除成员立即生效。规则：由被撤销密钥签的、不在撤销事件因果过去里的事件，一律拒收（与 Keyhive 的规则一致〔原文，高〕）。
- **回溯有上界**：撤销事件的 parents 由签名者自己填，可以倒填。所以只作废中继回执序号在撤销之后、或回执时间在撤销前 24 小时之内的事件；更早的要审批人另签一条显式列出事件哈希的 dispute（T2）。一致性用例里加"倒填 parents 的撤销"。
- 各类名册事件要什么签名，见 2.4 的矩阵。
- 生效后换代：审批人设备生成新的 epoch 密钥，分别封装给剩下的每台设备；中继白名单里删掉被移除的设备。
- 写入方加密前必须先和中继同步到最新名册，同步不了就不发（fail-closed，与放行一样）；读者看到移除之后仍用旧 epoch 加密的新事件时告警。
- 已经同步到对方设备上的历史数据收不回。这一点任何方案都一样，要写进告知书。

#### 1.5.4 本机副本的保护（两种模式）

| 模式 | 做法 | 未接受的他人正文 | 电脑上确认后 10 分钟延迟 | 安装 |
|---|---|---|---|---|
| **隔离模式（推荐，作为升级）** | 守护进程做成单文件二进制，装在 root 所有的路径；unit 文件只引用 root 所有的路径；以独立系统用户运行。Linux/WSL 用 systemd；macOS 用 LaunchDaemon 跑在独立用户下（不走"签名 app + keychain access group"那条路，所以不依赖登录钥匙串）。和本人进程之间用 Unix socket，访问控制靠 socket 所在目录的属主和权限：agent 和本人是同一个 uid，SO_PEERCRED 本来就分不出两者，Node 标准库也没有现成接口〔推断〕。spool 放在本人和守护进程共有的组目录。用签名的系统安装包（.pkg、.deb）安装，不在本人的 shell 里跑 sudo；自更新只接受发布密钥签名的包。副本、节点密钥、放行密钥对本人的系统用户（也就是 agent）不可读 | 电脑上没有能静默使用的钥匙（密码学闸门，前提见 1.5.5） | 由守护进程执行；**在下面的前提都成立时**，agent 绕不开 | 一次管理员授权 |
| 同用户模式（首次试用的默认；隔离前提不成立时的兜底） | 守护进程和 agent 是同一个系统用户 | 仍然解不开（密码学闸门不依赖隔离） | **执行不了**：agent 能直接读节点密钥和放行密钥，提前解开已转封的内容。所以这个模式下电脑上确认的放行类动作一律关闭，只能在确认设备上放行 | 不要管理员权限 |

**隔离的前提**。任何一条不成立，doctor 都自动降为同用户模式，电脑上的放行关闭：
- WSL 关掉 interop（`/etc/wsl.conf` 里写 `[interop] enabled=false`）。开着时，WSL 里的 agent 执行 `/mnt/c/Windows/System32/wsl.exe -u root` 就是 root，不要口令。代价：WSL 里不能再直接调用 Windows 程序（如 `code .`、`explorer.exe`）。
- 本人不在 docker、lxd 组里，没有免密 sudo，这些都等同 root。
- 守护进程的二进制、运行时和依赖都不在本人可写的位置，nvm 下的 `npm -g`、pipx 都不行。
- 节点公钥的指纹由 root 进程在安装器界面或新开的登录会话里显示，本人在手机上复核。这是为了防 agent 把电脑屏幕上的二维码和核对码换成自己的密钥。
- SECURITY.md 写明：装机之前 agent 已经在跑的机器不保证隔离，它可能早已劫持了 PATH 里的 sudo，或者弹过仿系统的口令框。

**缩小泄露的范围**：接受事件不把内容密钥转封给长期节点密钥，而是封给按天轮换的放行密钥。守护进程到点放行时解开，转存进本机加密存储，然后删掉当天的私钥。节点密钥即使泄露，也解不开历史上已经转封过的内容，包括已撤销、已作废的。

**秘密放哪**：连接器令牌等秘密由守护进程存在自己的受保护目录里，靠系统用户隔离保护。不用 Linux 和 WSL 的 Secret Service（它对同用户全开，无头守护进程也没有会话），也不用 macOS 的登录钥匙串（LaunchDaemon 用不了）。

这一节合并了两份笔记：local-first-sync 原来把节点密钥放在 `~/.longtable/`，human-confirm-local 要求隔离存储。合并后结论：**密码学闸门挡"没接受的"，隔离守护进程挡"接受了但还没到生效时间的"**，两者分工，缺一不可；两者都有前提，见上和 1.5.5。

#### 1.5.5 电脑浏览器里的人类密钥（残余风险，要实测）

- 问题不只在磁盘。WebCrypto 的"不可导出"只挡导出，不挡使用：同用户的 agent 能驱动浏览器（CDP、Claude in Chrome），打开中继源的页面，直接调用 `crypto.subtle` 用存着的密钥解封，不需要任何 UV。
- 所以只要登记了一把不需要 UV 的 desk 解密密钥，内容密钥就会封装给它，哪怕本人从不在电脑上看正文，agent 也能解开全部正文。上一版把条件写成"从不在电脑浏览器里看正文"是错的。
- 磁盘路径也很可能成立：Chromium 把 CryptoKey 结构化克隆后写进 IndexedDB 的 LevelDB，不经系统钥匙串〔推断，L0 闸门第 3 项实测〕。电脑被盗时同理。
- 任何在电脑屏幕上显示过的正文，同用户 agent 都能截屏或经 CDP 读 DOM。这是所有方案的共同上限，现行服务端方案里 agent 拿到 cookie 也一样。
- 做法（#28）：
  1. 电脑上不放能静默使用的解密钥匙。PRF 可用的平台，登记一把用 WebAuthn PRF 包裹的解密密钥：每次解封都要一次 UV，只在内存里用，绝不落盘。PRF 不可用的平台只签不解：别人的正文在手机上看、在手机上接受。
  2. 桌面网页不缓存任何明文或已解开的密钥，IndexedDB 里只存密文。
  3. 守护进程不对本人的系统用户提供任何返回未接受正文的接口，包括给网页用的 localhost 接口。SO_PEERCRED 和 TCP 都分不出浏览器和 agent。
  4. 残余：agent 如果在本人做 UV 的那一刻挂着调试器，能从页面内存里截下 PRF 输出，之后就能自己解封〔推断〕。写进 SECURITY.md；desk 解密密钥定期轮换。
- 结论：密码学闸门对"电脑上没有可静默使用的解密钥匙"成立，默认配置下对全体成员都成立；在电脑上解开、显示过的那一版正文，与现行方案持平。L0 闸门第 3 项和 L0 验收都加上"agent 经 CDP 或 Claude in Chrome 在页面里调用浏览器存着的密钥"这条用例，不只测磁盘。

#### 1.5.6 网页代码下发与中继运维方（B 新增的信任点）

- PWA 确认设备的代码从中继的源加载，RP ID 也是中继的主机名。能改这份网页包的人，就能在每个成员的确认设备上调用不可导出的 confirm 密钥：解开全部正文；在本人点"接受 T-63"时，让本人实际签下 T2 的 admit、共签或策略变更。
- 能改网页包的人包括：中继 root、云厂商、域名和 DNS 账号持有者、任何拿到部署凭据的进程。owner 的 coding agent 如果能用 owner 的 ssh 私钥或 ssh-agent 登录中继，也在其中。规划 D67③ 原本把 agent 的部署限制成 forced-command 的 rsync 加重启；而在 B 里，rsync 网页包恰好就是改所有人确认设备的代码。
- 同一个攻击者还能扣住手机发出的撤销。fail-closed 的规则是"同步过一次、没看到撤销就放行"，所以 10 分钟窗口也会失效。
- **结论：PWA 当确认设备时，中继运维方对明文和承诺都在信任范围内。**中继"只存密文"挡的是被动泄露（磁盘、备份、快照、托管商查看存储），挡不住主动改代码。这是所有网页端到端加密方案的通病；中心服务器方案里服务器本来就有明文，所以不算退步，但对外要说清楚（#1）。
- 两种常被提起的对策都挡不住，只能算**检测**：
  - service worker 激活新包前验签：浏览器更新 SW 时直接从网络取新的 sw.js，旧的 worker 拦不住也否决不了；首次安装时根本还没有 SW〔推断，基于 Service Worker 的更新流程〕；
  - `doctor` 每天比对中继上的网页包：中继能按设备白名单和 UA 只给手机下发恶意包，doctor 看到的永远是正版。
- 要做的事（L1，约 1 周，和发布密钥一起做）：
  1. 中继的管理凭据不放在任何成员电脑上 agent 够得到的地方：ssh 只用 ed25519-sk 加 verify-required（要触碰和 PIN）；云控制台开 MFA，不签发 API 密钥；doctor 检查 `~/.ssh` 里有没有能登录中继的普通私钥。
  2. 网页包不走 rsync：中继进程只接受项目发布密钥签名的包；当前版本的哈希由确认设备签一条 T2 事件钉住，各客户端和 doctor 都能比对。这挡住"拿到部署凭据"这一路，挡不住中继 root。
  3. 自托管指南写死：RP ID = 中继的确切主机名，这个主机不托管任何其他网页；验证者按创世事件里登记的 origin 精确比对（#11）。
  4. CSP 保持严格。
- 真正把中继移出信任范围的是原生确认 app：代码随签名的安装包分发，不经中继。Android 原生 app 什么时候做见 #12；iOS 原生 app 的分发路线在 L1 内定。团队里有用原生签名器的审批人时，只用 PWA 的成员签名册类 T2（admit、共签、reset、策略变更），还要该审批人共签。

#### 1.5.7 合规（要请律师重答）

- 项目不再是任何团队数据的处理者，每个团队自己是。owner 对自己的团队仍是处理者，D63 的告知书照样要签；C′ 试点沿用它。
- **去中心化并不消除出境**：境内成员的数据会同步到美国成员的设备上，这本身就是向境外提供。密文存在香港算不算出境，要请律师重答〔未核实〕。notifier 存的联系方式、时区和假期也放在香港，一并问（#10）。
- **被接受的正文会经 agent 发给模型厂商**：本人接受后，正文进本人的 agent，再发给 Anthropic、OpenAI 等模型厂商（规划第 0 节第 7 条的告知书已写）。B 的端到端加密管不到这一段，对外说"数据安全"时要写明。

### 1.6 没有中心服务器时，硬规则怎么保证

四条原则：
1. **验签的是每个读者**：违规事件在每个人的折叠里都无效，不依赖任何一台机器诚实；
2. **执行闸门的是被保护的那个人自己**：闸门保护的是本人的 agent，所以由本人的守护进程执行就够了；
3. **规则写在开源代码和公开规范里**，用共享的一致性用例锁住；
4. **折叠只以日志内容为输入**：时间相关的规则只用中继签名回执里的时间，客户端拒收时间倒退、或和本机时钟偏差超过阈值的回执；时间规则只决定事件什么时候纳入折叠，不决定它最终是否有效。每条事件带规则集版本号，规则变更由审批人签一条"规则版本"名册事件，在日志里的确定位置切换；读到更高版本的事件时 fail-closed，标"需升级"，不判有效。

| 规则 | 现行（服务端执行） | 去中心化后怎么保证 | 执行者 | 强弱变化 |
|---|---|---|---|---|
| H1 PAT 一律按 agent 记账；人类动作要本人的通行密钥断言；T2 另要确认设备签名 | 服务端验 PAT、会话、断言和设备签名 | 不再有 PAT。agent 只能经守护进程得到 agent 级签名。承诺类事件必须带人类签名，按名册登记的签名器类型判断：原生确认 app 的硬件密钥（每次使用由硬件强制人体动作）可以单独签；PWA 设备密钥必须和同一个摘要上 UV=1 的 WebAuthn 断言一起出现，缺一不可；desk 是 challenge 等于事件摘要、UV=1 的 WebAuthn 断言。只有 PWA 设备密钥签名的 T1、T2 一律无效 | 每个读者，在折叠时验签 | **更强**：任何成员都能独立复核，不依赖服务器诚实。残余同现行：电脑上的通行密钥能用口令满足；"看到的不一定是签的"，PWA 下还要加上中继运维方（1.5.6） |
| H2 T1/T2 清单 | 服务端按路由判断 | 清单写进协议规范；事件带 tier 字段；签名者的角色必须允许这个 tier：agent 和连接器永远不行，desk 只能签 T1，confirm 能签 T1 和 T2；名册事件按 2.4 的矩阵 | 每个读者 | 持平 |
| H3 绑定版本、through、参数；challenge 一次性 | 服务端生成 nonce，存 ceremony 表，同一事务里消费 | bind 元组和必绑字段表原样搬进事件。digest = SHA-256(域分隔 ‖ JCS(事件))，nonce 由签名方生成。through 改成"渲染时看到的事件头哈希集合"。"一次性"靠事件哈希去重。原来的 409 改成折叠时"作废，提示重签" | 每个读者 | 持平。这偏离了 WebAuthn L3"challenge 由 RP 随机生成"的 MUST〔原文，高〕：用途是内容签名，重放只会得到同一条事件。要在规范里写明；先例是 base-org/webauthn-sol 在链上验这种断言〔原文，高〕 |
| H4 闸门；10 分钟延迟；human_unverified | 服务端不下发 | ①密码学闸门（1.5.1、1.5.5）；②隔离守护进程执行 10 分钟延迟、撤销、"24 小时没在确认设备上 ack 就暂停"，时间按中继回执算，到点放行前必须同步过（fail-closed）；③电脑网页上不带人类断言的写入记为 human_unverified，读者按 agent 写的对待 | 本人的守护进程，加本人的人类端 | 未接受的正文：电脑上没有可静默使用的解密钥匙时**更强**（默认配置下是全体成员）；在电脑上解开、显示过的那一版与现行持平；PWA 成员对中继运维方见 1.5.6。延迟生效：隔离前提成立时持平；不成立或同用户模式下，改为只能在确认设备上放行 |
| H5 hooks、通知、AGENTS.md 只放 ID、计数、handle、枚举 | CLI 模板，加服务端常量模板 | 不变。通知由中继 notifier 用常量模板发，发送方只给它 handle、类别、哈希 ID | CLI、notifier | 持平 |
| H6 正文扫描，命中返回 422 | 服务端拒收 | 写入方客户端先拒；读取方再扫一遍（不能信别人的客户端），命中只遮蔽并标记 | 写方，加每个读者 | 略弱：改过的客户端能把违规内容写进日志，但在别人那里会被遮蔽 |
| H7 actor 四元组；会话防冒用 | 服务端 resolve_session | 事件由设备密钥签名，成员、客户端、机器都能验证。会话 ID 由本人守护进程从 stdio MCP 的环境里取，属于自报。冒用别人的会话不可能，因为签名密钥不同 | 成员和设备层：每个读者；会话层：本人守护进程 | 成员和设备层更强；会话层仍是本人自报 |
| H8 工具名、描述、instructions 都是常量 | 服务端 | 不变：本地 MCP，随签名发行版分发 | 发行版 | 持平；信任点从服务器移到发行版签名 |
| H9 凭据未经审批不生效；冷静期；数据库触发器 | 数据库触发器，加 `approve-first-owner` | 名册是一个签名 DAG，各类名册事件的签名要求按 2.4 的矩阵：首次登记要审批人签 admit（核对码）；加设备要确认设备发起、审批人共签、24 小时冷静期（按中继回执时间算）；撤销立即生效，作废的回溯有上界；纸质恢复密钥；3 人以上团队全部丢失时由 k=2 个审批人共签；并发冲突按 strong removal 处理；创世事件取代 `approve-first-owner` | 每个读者 | **更强**：没有服务器后门，也没有 root 能关掉的触发器。时间上要信任中继的回执，客户端对回执做时钟偏差检查 |

另外两条跨规则的变化：
- **数据库触发器（D67）**换成：每个副本里的校验代码、发行版签名、更新密钥离线保管、中继管理凭据只用硬件密钥、中继只接受签名的网页包。可复现构建放到首发之后。信任根从"服务器"移到"每台机器上的 app 二进制"，PWA 成员还要加上中继运维方。
- **新出现的威胁**（要写进威胁表）：
  - 中继运维方改网页代码（1.5.6）；
  - 同用户 agent 驱动浏览器使用人类密钥（1.5.5）；
  - 隔离前提不成立：WSL interop、docker 组、免密 sudo、可写安装路径、装机前已被劫持（1.5.4）；
  - 连接器以守护进程身份运行（4.3）；
  - 新旧内核版本混用、各副本时钟不同（原则 4）；
  - 队友的客户端被改：所有规则都在读者一侧验证，违规事件在别人的折叠里无效；
  - 本机信任锚被替换：team_id 和已验证的名册头必须放在 agent 改不了的地方，也就是隔离守护进程的目录里；否则 agent 能把本机指向一个伪造的团队分叉。

## 2. 人的确认

### 2.1 确认的本质变了

- **服务器版**：服务器校验一次 WebAuthn 断言，然后改数据库。
- **去中心化后**：本人的人类密钥对一条承诺事件签名，每个副本各自验签。

现行 H3 的 bind 元组、JCS 规范化、每类动作的必绑字段表，都原样搬进事件内容。另外三样换成新的承担者：

| 现行 | 去中心化后 |
|---|---|
| 服务器下发的 nonce | 事件自带的随机数和父哈希 |
| ceremony 表 | 日志本身就是证据 |
| 数据库触发器 | 每个副本里的校验规则 |

### 2.2 签名器分档

判断一把密钥能不能当"人类密钥"，看三条〔笔记 human-confirm-local，高〕：
1. 签名必须有人体动作，而且没有能靠打字满足的回退；
2. 绑在签过名的 app 身份上，不能只是一个文件；
3. 签名前给人看的内容，由 agent 改不了的界面渲染。

布尔型生物识别（LAContext.evaluatePolicy、Electron promptTouchID、Windows UserConsentVerifier、polkit）不产生可验证的签名，一律不用。

| 签名器 | 要人体动作 | 能靠打字绕过 | 绑 app 身份 | 弹窗显示动作 | 登记时能背书 | 定档 | 阶段 |
|---|---|---|---|---|---|---|---|

### 2.3 按成员情况推荐（L1 默认）

| 成员情况 | 确认设备（T2 和立即生效的 T1） | 电脑上的 T1（延迟生效） |
|---|---|---|
| iPhone + 任意电脑 | iPhone 主屏 PWA | 浏览器通行密钥（签名；PRF 可用时可以在电脑上解开正文，#28） |
| 不开代理也能用通行密钥的 Android（决策 spike 第 1 项实测） | Chrome 里的 PWA | 同上 |
| 大陆安卓（不论有没有 GMS），不开代理做不了通行密钥 | Android 原生确认 app（APK 直装；各家 ROM 对非商店安装的拦截要实测〔未核实〕）；有这样的成员时进 L1 | 同上 |
| 纯血鸿蒙，或没有合适的手机 | 没有。T2 用型号验过的 FIDO2 安全密钥，加审批人共签（D57、D66） | FIDO2 或浏览器通行密钥 |
| Linux 或 WSL 电脑 | 用手机 | FIDO2；守护进程以独立系统用户运行（WSL 要关 interop，1.5.4） |

手机确认不需要服务器，也不需要扫码回传。手机本身就是一个副本，经中继同步；它从自己验过的副本里渲染要确认的内容，签好的承诺事件直接追加进日志。二维码只当"打开 T-52"的指针，不承载内容，因为电脑上的 agent 能伪造二维码。

### 2.4 名册和流程

| 流程 | 去中心化后的做法 | 对应现行 |
|---|---|---|
| 建团队 | 创建者的确认设备签创世事件，里面登记中继 origin 和中继回执公钥；team_id = SHA-256(创世事件)；邀请链接里带 team_id 和中继地址，但单凭它拉不到日志（拉取要设备密钥挑战应答） | 取代 `approve-first-owner` |
| 首次登记 | 邀请链接（发邮件）加 8 位口头邀请码；新设备生成密钥，显示 6 位核对码 = H(team_id ‖ 全部新公钥 ‖ invite_id) 截断；审批人回拨入职时登记的电话，听成员报码，输入后在确认设备上签 admit；首次登记不走冷静期 | D56 原样 |
| 加设备或加桌面密钥 | 只能从现有确认设备发起；审批人在确认设备上共签；两个签名都到齐后再等 24 小时，**按中继回执时间算**，不按各副本的本机时钟；冷静期内新密钥签的事件先暂存，回执时间满 24 小时后才纳入折叠；期间本人任意一把人类密钥都能签 cancel。电脑节点密钥的指纹由 root 进程显示，在手机上复核（1.5.4） | D56、H9 |
| 丢设备 | 丢了电脑：在确认设备上签撤销（T2），立即生效。丢了唯一的确认设备：由审批人在自己的确认设备上代签撤销（T2）。不能撤掉自己最后一把 confirm 级密钥，除非替换的密钥已经在途 | D56 |
| 全部丢失 | 纸质恢复密钥（只显示一次，抄在纸上；只能签 recover）+ 核对码 + 审批人在确认设备上共签 + 24 小时冷静期。没有纸质密钥时，3 人以上团队由 k=2 个审批人共签 reset_member，并做视频核实、回拨电话；**2 人团队只能用纸质恢复密钥** | 恢复码改成纸质恢复密钥；"owner 重置"改成审批人共签 |
| 移除成员 | 审批人按门槛在确认设备上签 remove_member；之后换代 | D56 |
| 并发冲突 | 借 p2panda-auth 的 strong removal：被撤销者与撤销并发的操作作废，作废会传递给依赖它的操作；作废的承诺显示"需要重新确认"。回溯有上界：只作废回执在撤销之后、或撤销前 24 小时之内的事件，更早的要审批人签 dispute（1.5.3） | 新增 |
| 策略变更、规则版本 | 改门槛、加审批人、切换规则集版本都是 T2，要现有审批人按门槛共签 | 对应 D67"只能用一次" |

**名册事件 × 签名角色矩阵**（规范里写死；desk 弱档能被同机 agent 拿到断言，所以只给它最小的权限）：

| 名册事件 | 谁能签 | 档位 |
|---|---|---|
| undo；cancel 本人的待生效项 | 本人任一人类密钥（含 desk） | T1 |
| 撤销本人的 desk 密钥 | 本人任一人类密钥（含 desk） | T1，立即生效，只收紧本人 |
| 撤销 confirm 级密钥（包括本人的）；代签他人的撤销 | 确认设备 | T2 |
| admit；加设备或加桌面密钥的发起和共签 | 发起：本人确认设备；共签：审批人确认设备 | T2 |
| reset_member；recover 的审批 | 审批人确认设备（3 人以上团队 k=2；2 人团队不可用） | T2 |
| remove_member；换代；策略变更；规则版本 | 审批人确认设备，按门槛共签 | T2 |
| 启用连接器（登记子密钥和清单哈希） | 本人确认设备；工作区级连接器另要审批人 | T2 |
| dispute（显式作废列出的事件） | 审批人确认设备 | T2 |
| 钉住网页包版本哈希 | 审批人确认设备 | T2 |

团队里有用原生签名器的审批人时，只用 PWA 的成员签上表中的 T2，还要该审批人共签（1.5.6）。

设计借鉴 @localfirst/auth（MIT，npm 6.0.0，2024-11；维护是否活跃〔未核实〕，所以只借设计）和 p2panda-auth（API 不稳）。不依赖 Keyhive：官方写明"pre-alpha … DO NOT use this release in production"〔原文，高〕。

### 2.5 延迟生效、撤销、上限由谁执行

- 把内容放行给"我的 agent"，只发生在本人电脑的守护进程里。其他成员只需要把状态显示对，例如"李已在电脑上接受，HH:MM 起对李的 agent 生效"。
- effective_at = max(签名方自报时间, 中继回执时间) + 10 分钟。用回执时间而不是本机收到的时间，所以各副本算出的结果一致；自报时间在人类签名的覆盖范围内，agent 伪造不了。离线签的承诺，拿到中继回执后才生效。
- 每天 6 次、每小时 3 次：签名端在签之前先拦（防 MFA 疲劳），各副本再按日志复核。超限的事件标成"需要在确认设备上重新确认"，不直接丢弃。
- 确认设备首页的"在其他设备上确认的动作"清单：手机从日志里筛出本人用桌面档签的事件，请本人再签一条 ack。按回执时间超过 24 小时没 ack，本人的桌面档签名器暂停。全程不需要服务器。

| 3 | **我的 agent 能看到什么**（闸门与承诺账本 + 本人会话地图） | Q5、Q6、Q8 | 三块：①还没放行 / 待生效（"09:22 起生效，还可以撤销 8 分钟"，今日 2/6）/ 已放行，每条都能切到"agent 视角"，显示守护进程给 agent 的原样输出；②承诺账本：我答应别人的、别人答应我的，附签名证据；③本人会话地图：只给本人看。另做 Claude Code 状态栏（例："邻桌 本会话→T-57 · 待您 3 · 王 当地 18:12 下班后"）和页脚链接 | 7–8 人日 |

三个合计约 18–22 人日，排在 L2。L1 只顺手做两件各 0.5 天的零风险小事：
- 用 `footerLinksRegexes` 让输出里的 T-、B- 编号变成可点的链接；
- 首页"待我处理"把"我的 agent 在等我"的几类合并显示。

所有派生都写成 TypeScript 纯函数 `derive(snapshot, viewer, now, calendars)`，配 JSON 用例，和内核同一套技术栈。

### 3.3 载体与设计原则

| 载体 | 放什么 | 优先级 |
|---|---|---|
| 手机 PWA（也是确认设备） | 首页顶部"在等您"、"在其他设备上确认的动作"、接受和转发、"您不在的时候" | 最高 |

| Claude Code 状态栏 | 一行：本会话的任务、待处理计数、对岸成员的当地时间。只读本地缓存，p95 ≤ 50ms；只放 ID、计数、handle（H5）；不覆盖用户已有的状态栏，已有时只给一段可拼接的片段 | 高（1–1.5 天） |
| Claude Code 页脚链接 | T-、B- 编号变成可点链接 | 高（0.5 天，性价比最高） |
| 终端 `status` / `watch` / `--line` | 视图 1 和视图 3 的文字版；供 tmux 用。Codex 用户靠它代替状态栏 | 中（2–4 天，已计入 L2） |
| 邮件摘要 | 只写"有 N 件在等您，打开 app 查看"，不带标题（1.5.2）；带标题的"您不在的时候"在 app 里看 | 随 notifier |
| Tauri 菜单栏 | "待我 N" | 低，按信号（1–2 周） |

设计原则（详见笔记 ui-visualization 第 5.4 节）：
1. 先文字后图形：每个视图都有等价的表格或列表，读屏软件读表格；
2. 按对象聚合，不按人统计：没有个人图表和排行；
3. 时长按"该动手的那个人"的工作时间算（"张今天休假，不计时"）；
4. 跨两侧的时间两边都写（"王当地 00:12，即您的 15:12"）；
5. 一处真相："agent 视角"和 agent 真拿到的内容用同一个序列化函数；
6. 永不变黑：没有动静本身也要渲染成状态（借 Buzz），但只给本人看；
7. 失败和等待上浮，例行动态下沉；
8. 状态用词，不用颜色；不用 emoji 和彩色 chip；
9. 中英双语按查看者切换，英文也用大家熟悉的功能名（Accept、Claim、Forward、Comment、Publish）；
10. 无障碍：语义化表格、全键盘操作、`aria-live="polite"`、手机正文不小于 16px。

本地优先带来的体验（对 Multica、Paperclip 的网页端是改进，但不是 B 独有）：
- 先从本机副本渲染（目标首屏 300ms 内〔推断，需实测〕）。中心服务加客户端同步引擎也能做到：Linear 的本地同步引擎是它的招牌〔笔记 ui-visualization，未核实细节〕，Multica 有桌面版，路线 C 加一层 IndexedDB 缓存同样能先渲染本地数据；
- 离线可读，同上；
- **离线确认（先签、后同步）是 B 独有的**；
- 会话细节只存在本人设备上：要配合 1.5.2 的元数据最小化（回合结束、工具映射、心跳只留本机，agent 级事件按小时批量、时间取整），"本人看全、队友看粗"才在架构上成立，不只是界面上的承诺；
- 看板可以折叠到任意时刻回放（L4，3–5 天）。

对外和在 B、C 的取舍里，不再把秒开、离线可读算作 B 独有的卖点。

### 3.6 与规划 7.4「不监控人」的冲突（待拍板 #17）

课题要求显示"每个人的 agent 会话多久没动、是否卡住"，这和 7.4 直接冲突：7.4 规定队友只显示"在做什么"和"今天有更新"，不显示分钟数、回合数、提交频率。推荐不放宽：
- 本人能看每个会话"上回合结束多久了"、是否已结束、hooks 是否静默；
- 队友只按**任务**看三档："今天有更新 / 1 个工作日没有更新 / agent 已离线"；
- "卡住"只认显式的困难对象，不从空闲时长推断。
- 架构上也要守住：回合结束、工具映射、会话开始和结束、心跳只留本机；agent 级事件按小时加抖动批量上传，时间取整到小时；中继默认不记访问日志（1.5.2）。否则中继管理员（通常就是 owner）和任何队友的副本都能算出每个人 agent 的逐回合时间线。

**读出来的结论**：
1. 对手说的"能接多少种 CLI"，指的是"能拉起多少种"。去比这个数，就要也去拉起 agent，背离"不替人跑 agent"的定位。
2. 能接你自己会话的，都只是"让模型自己去调"，模型忘了就没有；**团队协作产品里没有一家装 hooks**。单人工具已有先例：Emdash 往支持 hooks 的 agent 的用户级配置里装带标记的条目，Warp 也装 hooks〔笔记 connectivity，原文 Emdash README〕。
3. IM 在对手那里是"agent 的嘴"，消息直接进下一次 run。对我们这是注入入口。
4. 工单连接要公网 IP；中国平台（Gitee、飞书项目、TAPD、CNB）没人接。
5. 人的通知是普遍短板，用 Apprise 一步就能拉开差距。

### 4.3 我们的连接器架构

**四类连接器**：

| 类 | 例子 | 跑在哪 | 能产生的事件 |
|---|---|---|---|
| A agent 适配器 | Claude Code、Codex、Qwen Code | 成员本机（hooks 调本地入口；stdio MCP） | 会话开始和结束、回合结束、提交、工具调用归属；agent 级看板事件 |
| B 工单 | GitHub、Gitee、Linear | 成员本机（谁动手谁同步）；可选由团队中继收 webhook，但中继上只能"收外部数据 → 封给成员密钥 → 用中继连接器子密钥签名"，清单里 `runs_on` 含 relay 时不许有 `reads` | 外部链接、外部状态观测、外部任务提议 |
| C 聊天 / 通知 | Apprise 渠道、飞书长连接 | 中继上的 notifier（只收 handle、类别、哈希 ID）；零常开机器模式下由事件作者本机用收件人的投递令牌发；入站机器人放在收件人本机 | 通知回执；入站只有查询和跳转 |
| D 协议桥 | AAMP、ACP 启动器、MCP 通用工单 | 成员本机；要在中继上解密的桥单列"中继可解密"一档，开启算 T2（1.5.2） | 外部任务提议、状态观测 |

**agent 适配器做成数据，不做成代码**：
- 每个 CLI 一份 `agents/<id>.toml`，写探测路径、MCP 和 hooks 写入器、事件映射、输出编解码、会话 ID 来源、验证过的版本范围、skill 目录。
- 只有一个 hook 入口：`<标识> hook <事件> --agent <id>`，一旦发布就冻结（沿用 D27）。
- 社区加一个同形的 CLI，只要提一个 TOML 文件加用例。

**连接器清单和权限执行**（按强弱排）：
1. **事件类型白名单在每个客户端验签时执行**：连接器用角色为 connector 的子密钥签名，它签出来的承诺类事件在所有客户端里一律无效。这和"agent 密钥签的承诺无效"是同一条规则，不靠连接器自觉。
2. **子密钥由守护进程持有**：连接器只能请求签名，守护进程按清单里的 `emits` 白名单代签。否则连接器跑在本人 uid 下时，同用户 agent 能冒充任何连接器，签出假的"GitHub 上指派给您"。
3. **进程身份**：第一方连接器在守护进程内运行。第三方连接器必须跑在独立的低权限系统用户下，或者强制沙箱里（Linux 用 bubblewrap，macOS 用 sandbox-exec），只从守护进程交给它的 fd 读投影数据；做不到就不在电脑上运行。作为守护进程的普通子进程，它会继承守护进程的身份，读得到节点密钥、全量副本和 epoch 密钥。
4. **数据投影在守护进程里执行**：连接器只拿到清单 `reads` 里列的字段；正文、评论、闸门后面的内容永远不给。
5. **启用要在确认设备上确认**：启用任何连接器都是 T2，同时把连接器子密钥和清单哈希登记进名册（2.4 矩阵）。外发标题的（`exports_titles_to` 非空）另外列进"数据去向"页（例如"标题和状态会发到 github.com"），工作区级的还要审批人。
6. **外部事件按 agent 级信任显示**：队友那里显示"经 GitHub 连接器（张三的电脑）"，计入扇出限额，不算人的承诺。
7. **出网**：第一方连接器共用一个只放行清单域名的 HTTP 客户端；第三方连接器靠第 3 条的沙箱限制。
8. **秘密**放在守护进程自己的受保护目录里（1.5.4），不进事件日志，不进中继。不用 Linux 和 WSL 的 Secret Service（对同用户全开，无头守护进程也没有会话），也不用 macOS 的登录钥匙串。
9. **通知渠道防 SSRF**：Apprise 只放行白名单里的 scheme；渠道 URL 由成员自填，所以禁止解析到内网、回环和链路本地地址（包括云厂商的元数据服务和中继本机的管理接口）。

**工单规则**：
- 只同步元数据：外部 ID、链接、标题、状态、负责人、更新时间。不同步正文、评论、附件。
- 外部标题按 agent 标题的规则清洗，在信封里标 `trust: external`。
- **外部指派不等于接受**：外部指派进"待您接受"。
- **谁动手谁同步**：用这个人自己的令牌写回外部，没有共享的机器人令牌。
- 轮询用 ETag：GitHub 认证的条件请求返回 304 时不计入主速率限制〔原文，高〕。
- 不需要公网 IP。

**分发**：
- 第一方连接器随核心包发布：PyPI、npm，国内走镜像（npmmirror、PyPI 国内镜像）；Gitee Releases 放离线包（Gitee 的实名和审核现状〔未核实〕）。
- 守护进程和其他原生部分按 esbuild / @napi-rs 的方式发布：每个平台一个 npm 子包，经 `optionalDependencies` 安装，npmmirror 能直接提供（例如 @napi-rs/keyring 2.1.0，2026-09-13 发布，自带 darwin、linux、win32 子包〔原文 npm，高〕）。禁止 postinstall 联网下载，不用 node-gyp：keytar 7.9.0 的安装脚本要从 GitHub Releases 下载预编译件〔可行性评审，原文 npm〕，peercred 1.1.2（2016-07-12）的安装脚本是 `node-gyp rebuild`〔原文 npm，高〕，在国内和单二进制打包里都会出问题。
- 第三方连接器的索引是一个 git 仓库，GitHub 和 Gitee 双源。
- MCP server 发布到 MCP Registry；插件进 Claude Code marketplace。

**一键接入**：`setup` 先探测已装的 CLI，列出每家能接到几级，一次确认后写入。支持 `--dry-run` 和 `--undo`，重复运行字节不变，D43 的合并规则推广到所有写入器。

## 5. 开源免费与合作方案

### 5.1 许可证建议

| 组件 | 许可证 | 说明 |
|---|---|---|
| CLI、hooks、本地 MCP、守护进程 | Apache-2.0 | 规划 10.4 本来就定客户端用 Apache-2.0；"能审计上传了什么"是采用理由 |
| 网页 app | Apache-2.0 | 本地优先下它是客户端 |
| 中继、notifier | Apache-2.0 | 端到端加密之后，我们没有托管服务要保护 |
| 连接器 SDK、示例 | Apache-2.0 | 第三方连接器可以用任何许可证 |
| 协议规范 | Apache-2.0 | 与 MCP 规范一致，任何项目都能实现，包括 Multica |
| 文档、教程 | CC-BY-4.0 | 与 MCP、Agent Skills 一致 |
| 公开的注入回归语料 | CC-BY-4.0 或 CC0 | 样本里不能有真实数据 |
| 名字、标志 | 不放进开源许可证，另立 TRADEMARKS.md | 改过的 fork 要换名字；只有通过兼容性测试的实现才能标"Longtable compatible" |

**为什么不用其他许可证**：

| 选项 | 不用的理由 |
|---|---|
| Apache 加附加条款（Multica、Dify 那种）、BUSL、FSL | 不是 OSI 许可证〔原文 SPDX，高〕，和"开源"对不上；规划 10.4 已经排除 |
| 中继用 AGPL | 只防"改过的中继对外服务"，挡不住别人托管原版；中继只有一两千行，重写很便宜；不少公司内部禁用 AGPL〔背景〕；AI 生成代码的版权不确定，会削弱 copyleft 的执行力〔需律师〕 |

**先宽后紧更容易**：Apache-2.0 的代码可以并入 AGPLv3 作品，所以以后中继要改 AGPL，新版本直接换就行；反过来要所有贡献者同意〔背景，需律师确认〕。AGPL 只在两种情况下启用：出现伤害用户的闭源公共中继；owner 决定做付费托管中继。

**贡献规则**：
- 用 DCO（每个提交带 `Signed-off-by`），不签 CLA。
- 这一点本身就是卖点，和 Multica 形成对比：Multica 的贡献条款写的是"出品方可以把许可证改得更严或更松"，贡献"可用于出品方的云业务"〔原文 Multica CONTRIBUTING、LICENSE，高〕。
- 代价是以后不能把社区贡献改成商业许可证去卖。

**防抄靠什么**：
- 机制容易抄。取舍是不是难抄，要看对手怎么跟：做成工作区级的默认关闭开关，就不必拆审批自动应答和 @ 触发 run（调研笔记已预判 c1 的 PR 会被"改成默认关闭"）。所以上一版"取舍难抄"的说法偏乐观，剩下什么见 5.6；
- 名字被冒用靠商标；
- 开放规范和"compatible"标签能把别人吸收我们的机制变成和我们兼容，但前提是目标定为推广规范（#22）。

### 5.2 可持续性

| 成本 | 谁出 | 量级 |

### 5.3 合作、借用、兼容：逐项评估

| 对象 | 许可 / 现状（核实） | 可选的合作形式 | 对 H、C、G 的影响 | 工作量 | 结论 |

### 5.6 对手把机制做成可选开关之后，我们还剩什么

开放规范附一致性用例，对手照着实现只要几周。研究笔记已经预判：Multica 跟进时会做成"默认关闭"的可选项，不必拆它的卖点。所以要按"对手 2027 年已经跟进"来想：

| 现在的差异 | 对手跟进的难度 | 跟进之后还剩什么 |
|---|---|---|
| 承诺只归人、接受闸门 | 低：做成工作区级、默认关闭的开关 | 我们默认开、不能关；在对手那里是可选项。对在意的团队有吸引力，对不在意的没有 |
| 端到端加密的本地优先架构 | 高：中心服务要改存储和鉴权 | 中继看不到明文、离线确认。对 2–5 人团队价值有限（1.2） |
| hooks 深接 5 家以上 CLI | 中：适配表公开；Multica 4 人、几乎每个工作日发版 | 先发优势，靠持续维护 |
| 中美接力视图、按工作时间计时 | 中：要有成员时区和日历数据 | 先发优势，场景专注 |
| 中国可达（镜像、国产 CLI、国内通知渠道） | 低到中：Multica 中文好、国产 CLI 多 | 两地实测表 |
| 开放规范和 compatible 标签 | — | 规范维护者的身份 |

结论：
- 这些都不是持久的护城河。加起来是"专注中美小团队、默认安全"的组合，加上执行速度。
- 够不够，要看首发后 8 周的外部团队数（#26、7.5）。
- 目标定为"让用户选我们"时（#22 默认），不主动把机制送到对手手里，邀请等有外部用户之后再发。目标定为"推广规范"时，对手采用就算赢，成功指标换成实现数。两种目标下的推荐不同，所以请你明确。

**为什么推荐 TS 统一内核**：
- 手机和电脑浏览器本来就必须跑 TS 的折叠和验签。
- 验签、名册、strong removal、延迟规则都是安全关键代码，两份实现一旦漂移，就会出现"不同成员看到的承诺不一样"。笔记 local-first-sync 把这列为最大的隐藏成本。
- 本机守护进程用 Node 跑同一份代码，MCP 有官方 TS SDK。
- Python 只留 hook 快速路径，它本来就只读缓存、写 spool，用标准库，p95 ≤ 50ms 已经实测达标〔规划 D48，高〕。

**按模块汇总**：M0 实测 server 5,355 行、CLI 3,996 行、web 3,150 行〔原文 wc，高〕。按 TS 列，能复用的代码只有 CLI 的 hook 路径和网页组件，约占 M0 的 40%；内核代码复用为 0。所以 L0 的内核按"约一半规则新写"估 4–6 周，不是上一版的 3–4 周；L0 验收用规则覆盖矩阵，不用"≥200 条、大部分从 M0 转写"，后者靠清洗语料就能凑够，会遮住新规则没有测试的空白。C′ 用的是 M0 本身，复用约 90%。

**代价**：
- 装机要同时有 Python 和 Node 两个运行时。守护进程用 Node SEA 或 `bun build --compile` 打成单个二进制，装在 root 所有的路径（1.5.4）；原生部分按每个平台一个 npm 子包发布，禁止 postinstall 联网和 node-gyp（4.3 分发）〔推断〕。
- `service.py` 的代码复用从约 60% 降到"只复用设计"：L0 多约 1–2 周，但 L1 网页阶段省约 1–1.5 周，长期维护量减半〔推断〕。

### 8.2 未核实清单（查不到或被代理挡住，不能当事实用）

**同步与传输**：
- Gitee 的镜像功能、美国成员能否注册、私有仓库的人数上限；
- 腾讯云 COS 和阿里云 OSS 是否支持条件写；AWS S3 条件写本次没读到原文；
- Cloudflare R2 和 Tunnel、Tailscale、iroh 公共中继、Nostr 公共 relay、ntfy.sh 在国内的可达性；
- 国内家宽是否普遍没有公网 IPv4、封 80 和 443。
- 境内机器对外提供服务时 ICP 备案的具体要求；
- GitHub 规则集能不能保护 `refs/heads/` 之外的自定义 ref。
