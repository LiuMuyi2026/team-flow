# 守住「只有人能答应」，邻桌才能突围

截至 2026-10-03，「团队里人人用 CLI 编程 agent」的协作工具已经扎堆：GitHub、Linear、Jira、Notion 都能把工单交给 Claude 或 Codex，Anthropic 和 OpenAI 各有自家的团队功能，开源侧 2026 年冒出了 Paperclip（9.6 万星）、Multica（5.2 万星）、Block 的 Buzz、OpenAI 的 Symphony 和 YC 的 qm，中国有腾讯 CodeBuddy NPC 和飞书项目的 AAMP 协议。**它们几乎都由产品自己启动或托管 agent**（云端运行、本机 daemon、心跳或无头桥），没有一家用 hooks 把每个人正在用的交互式 Claude Code / Codex 会话自动接到一块带指派、认领、困难的共享看板上（Multica、Paperclip、Agor 只留了让模型自己去调 CLI 或 MCP 的侧门），也没有一家同时做到「agent 不能替人答应」「同事写的文字要本人接受才进自己的 agent」和「跨人的谁卡住、需要谁」，这是邻桌（Longtable）真实存在的空位。但这个空位窄，而且大部分能被抄走：hooks 自动上报（Emdash、Warp 已在单人工具里用）和困难对象，Multica 补起来不难；真正难抄的只有逐条接受的闸门和「承诺只归人」这套取舍，因为它和对手们「无人值守、一句话派活」的方向相反，而它恰恰也是邻桌最费事、最可能被用户嫌烦的部分。邻桌的劣势同样实打实：还没上线、零外部用户、一名开发者、Codex 一侧只做过模拟，没有 GitHub 关联、没有自动执行、没有社区；最危险的对手 Multica 是香港公司，大多数工作日都发版，已接飞书、钉钉、企业微信和 26 种 CLI。建议的顺序是：先按计划做完 M1 并用真实 Codex 跑通，用两周内部试点检验闸门的代价（规划已有止损线）；再补 GitHub PR 关联、开源客户端、公开安全模型；对外定位为「agent 汇报、人来答应」的承诺台账，按活跃的人低价收费、agent 免费，明确不做自动执行、不做通用工单、不追 CLI 数量。

**来源标注**：〔原文〕指调研时读到了页面本身，或项目自己的仓库文件（README、文档、规范、许可证）和机器数据（npm、Go module proxy、每日 GitHub 排名 CSV）；项目文档描述的行为都没有经过运行验证。〔摘要〕指页面被代理挡住，只看到搜索引擎摘要。〔二手〕指第三方聚合站、评测或竞品写的分析，可信度最低。所有来源都在 2026-10-03 检索，正文里的日期是事件或发布日期。邻桌的现状以本次任务简报和规划文档（`/home/user/team-flow/docs/plan.md`，下称「规划」）为准，计划中的功能一律标「计划」，标「推断」的是调研或本报告的推理，不是来源原话。

## 赛道已经挤满，但几乎所有人都在替你跑 agent

2026 年，「人和 agent 同在一块板上」从概念变成了每家都在做的功能。四类玩家打法不同，前提却一样：agent 由产品自己启动或托管。

### 大厂把 Claude 和 Codex 拉进自家云端工单

GitHub 是覆盖最全的跨厂商入口。Claude 和 Codex 在 2026-02-02 以公开预览进入 Agent HQ，2026-02-26 扩到 Copilot Business 和 Pro（〔原文〕[GitHub 社区 #186179](https://github.com/orgs/community/discussions/186179)）；一条 issue 可以指派给 Copilot、Claude 或 Codex，但**每次运行都是 GitHub 托管的云端会话，按 Actions 分钟和 AI Credits 计费，单次最长 59 分钟、一个任务只出一个 PR**，第三方 agent 在当前文档里仍是公开预览（〔原文〕[About third-party coding agents](https://raw.githubusercontent.com/github/docs/main/content/copilot/concepts/agents/about-third-party-coding-agents.md)、[About Copilot cloud agent](https://raw.githubusercontent.com/github/docs/main/content/copilot/concepts/agents/cloud-agent/about-cloud-agent.md)）。Linear 的模型是「issue 只能指派给人，只能委派给 agent」，人始终是负责人（〔摘要〕[Linear Docs](https://linear.app/docs/assigning-issues)）；2026-06-11 上线的 coding sessions 把委派出去的 issue 交给 Claude Code 或 Codex 在 Linear 的云沙箱里跑，按 AI credits 计费（〔摘要〕[Linear changelog](https://linear.app/changelog/2026-06-11-coding-sessions)），而请求原生 Claude Code 委派的 issue 自 2025-12-03 一直开着、无人回应（〔原文〕[claude-code #12925](https://github.com/anthropics/claude-code/issues/12925)）。Jira 在 2026-07-15 支持把工作项指派给 Claude Code、Cursor 和 Copilot，并加了「Jira 里的 agent 会话」，付费 Jira Cloud 不加价，Codex「即将支持」（〔摘要〕[SiliconANGLE](https://siliconangle.com/2026/07/15/atlassian-evolves-jira-orchestration-hub-developers-ai-agents/)、[DevOps.com](https://devops.com/atlassian-extends-ai-reach-of-jira-into-agentic-engineering-workflows/)），前提是开通 Rovo（〔原文〕[GitHub Docs：Jira 集成](https://raw.githubusercontent.com/github/docs/main/content/copilot/how-tos/copilot-integrations/integrate-cloud-agent-with-jira.md)）。概念上离邻桌最近的大平台是 Notion：2026-05-13 的 External Agents API（alpha）让团队在共享看板上把任务指派给 Claude Code、Codex、Cursor 并实时看进度，每个 agent 单独授权、不继承发起人的权限（〔摘要〕[Notion releases](https://www.notion.com/releases/2026-05-13)、[Notion Help](https://www.notion.com/help/use-claude-agents-in-notion)）。

两家模型厂商只做自家 agent 的团队功能。Anthropic 的 agent teams 有共享任务列表、文件锁认领和依赖，但**任务列表只存在本机、从不上传，一个会话只能有一个团队**，功能本身还是实验性、默认关闭（〔原文〕[Claude Code Docs：agent teams](https://code.claude.com/docs/en/agent-teams)）；面向多人的是 2026-06-23 上线的 Claude Tag，Slack 频道里谁都能 steer 同一个 @Claude，仅限 Team/Enterprise，按组织用量计费（〔原文〕[Claude Tag overview](https://claude.com/docs/claude-tag/overview)、[How Claude Tag works](https://claude.com/docs/claude-tag/concepts/how-it-works)；〔摘要〕[VentureBeat](https://venturebeat.com/technology/anthropic-launches-claude-tag-replacing-its-slack-app-with-a-persistent-ai-teammate-that-learns-monitors-and-works-autonomously)）。OpenAI 在 2026-09-29 的 DevDay 发布了团队共享的云环境、CLI 的 `/agents` 视图、Business/Enterprise 的 Team Tasks，以及含审批的工作区 Agent Security 策略（〔摘要〕[OpenAI DevDay 2026 回顾](https://openai.com/index/devday-2026-recap/)）。Slack 成了各家机器人的集散地，Dreamforce 2026 推出让人和 agent 同看计划、diff 和预览的 Slack Code 频道（〔摘要〕[Salesforce](https://www.salesforce.com/news/stories/five-dreamforce-2026-takeaways/)）。这些大平台有三个共同点：**agent 都在平台或厂商的云里跑**，工程师本机的交互会话在这些视图里看不到（推断）；没有认领、困难、请人帮忙这类跨人对象，人的闸门设在合并（agent 不能批准或合并自己的 PR）而不是承诺；团队功能大多锁在 Business/Enterprise 档。而且方向是继续放权：2026-09-01 起，管理员开启后 Copilot code review 可以批准 PR（〔摘要〕[GitHub Changelog](https://github.blog/changelog/2026-09-01-copilot-code-review-can-now-approve-pull-requests/)）。

创业公司说的「团队」有两种意思。一种是一个人同时开很多 agent 的桌面工作台，Conductor 在 2026-03-30 拿到 2,200 万美元 A 轮（〔摘要〕[Conductor](https://www.conductor.build/blog/series-a)）；另一种是团队从 Slack、Linear 触发的云端 agent，Devin 的母公司 Cognition 在 ### 开源星数涨在「替你跑 agent」的平台上

按 2026-10-03 的 GitHub 排名数据，关注度集中在团队级平台：**Paperclip 96,372 星、9 月一个月涨 16,475；Multica 51,861 星、9 月涨 3,202**；Block 的 Buzz 35,426 星、9 月涨 3,426；OpenAI 的 Symphony 27,511 星、9 月只涨 505；Vibe Kanban 28,249 星，已宣布停止（〔原文〕[排名 2026-10-03](https://raw.githubusercontent.com/EvanLi/Github-Ranking/master/Data/github-ranking-2026-10-03.csv)、[排名 2026-09-03](https://raw.githubusercontent.com/EvanLi/Github-Ranking/master/Data/github-ranking-2026-09-03.csv)）。这些平台都由产品自己跑 agent：Multica 用每人机器上的 daemon，Paperclip 用心跳，Agor 在共享主机的浏览器工作区里跑，Buzz、Symphony、qm 各自拉起或托管 agent（逐项见下一节）。协调原语那一层（MCP 邮箱、文件租约、交接工具）项目多、寿命短，GNAP、Swarm Protocol 在 2026 年春季活跃后一到三个月就停了（〔原文〕[awesome-agent-orchestrators](https://github.com/andyrewlee/awesome-agent-orchestrators)）。与邻桌设计相关的零件散在各处：Concord MCP 要求接收方 accept 之后所有权才转移（〔原文〕[Concord MCP](https://github.com/Get-Concord-AI/concord-mcp)），AMP 协议给跨租户消息加信任等级并强制用 `<external-content>` 包裹（〔原文〕[AMP 安全规范](https://github.com/agentmessaging/protocol/blob/main/spec/07-security.md)），batonpass 和 abevz/dibs 用 SessionStart hook 注入上下文并声明「是数据，不是指令」（〔原文〕[batonpass](https://github.com/solsebb/batonpass)、[dibs](https://github.com/abevz/dibs)）。但调研读过的 46 份 README 里**没有一份提到 passkey、WebAuthn 或 FIDO**，反倒有不少工具默认跳过权限确认。许可证也划了线：Multica 的附加条款禁止为组织外的用户提供托管服务，免费也不行；Agor 的 BUSL-1.1 在 2029-01-15 之前禁止做「Agor Offering」（〔原文〕[Multica LICENSE](https://raw.githubusercontent.com/multica-ai/multica/main/LICENSE)、[Agor LICENSE](https://raw.githubusercontent.com/preset-io/agor/main/LICENSE)）。想做托管产品就不能拿这两家的代码改，这也印证了规划 D01「自建薄服务」的理由。

### 中国市场：国产 CLI 快速换代，飞书和腾讯各自入场

国内大厂都已有仿 Claude Code 的终端 CLI，腾讯 CodeBuddy Code 在 npm 上已发 1,355 个版本，阿里有 Qoder CLI 和开源的 Qwen Code，月之暗面有 Kimi Code（〔原文〕[npm：CodeBuddy Code](https://registry.npmjs.org/@tencent-ai%2fcodebuddy-code)、[Qwen Code](https://github.com/QwenLM/qwen-code)、[Kimi Code](https://github.com/MoonshotAI/kimi-code)），但它们的「团队」功能主要是席位、积分池、SSO 和审计，例如 CodeBuddy 团队版每席每月 40 美元、积分全队共享（〔摘要〕[腾讯云价格说明](https://www.tencentcloud.com/document/product/1256/77270)）。换代极快：iFlow CLI 2026-03-20 停止维护，通义灵码 2026-05-20 改名 Qoder CN，百度 Comate 2026-09-07 并入 DuMate（〔摘要〕[iFlow 社区公告](https://vibex.iflow.cn/t/topic/4819)、[阿里云开发者社区](https://developer.aliyun.com/article/1740785)、[新浪科技](https://finance.sina.com.cn/tech/2026-09-07/doc-iniqyvrz0383318.shtml)），原 Kimi CLI 2026-09-23 归档（〔原文〕[kimi-cli](https://github.com/MoonshotAI/kimi-cli)）。真正能「把活派给 agent、看它做完」的是 2026-07-23 发布的**腾讯 CodeBuddy NPC**：在腾讯 CNB 的 Issue、PR 或评论里 @NPC，它规划、写代码、开 PR、跑测试、按 CI 结果自修，还能组成由 PM NPC 拆活派活的「NPC Teams」（〔摘要〕[IT之家](https://www.ithome.com/0/980/633.htm)、[网易](https://www.163.com/dy/article/L2HI90JF0511B8LM.html)）。字节走得最远：**飞书项目在 2026-04-23 把自己定位为「人+Agent 协同的行动系统」**，同时开放了以邮件为载体的 AAMP 任务协议（〔摘要〕[量子位](https://www.qbitai.com/2026/04/406026.html)），飞书官方 CLI 自称「为人和 AI Agent 而建」，有 17.5k 星（〔原文〕[larksuite/cli](https://github.com/larksuite/cli)）；钉钉也开源了原生支持 Claude Code 和 Qoder 的 CLI（〔摘要〕[量子位](https://www.qbitai.com/2026/03/392828.html)）。社区早已把 Claude Code、Codex 接进国内 IM：cc-connect 有 15.7k 星，lark-coding-agent-bridge 有 2.6k 星，飞书官网还为后者写了教程（〔原文〕[cc-connect](https://github.com/chenhg5/cc-connect)、[lark-coding-agent-bridge](https://github.com/zarazhangrui/lark-coding-agent-bridge)）。Multica 在中国同样走红，带中文 README 和飞书、钉钉、企业微信机器人（〔原文〕[Multica README](https://raw.githubusercontent.com/multica-ai/multica/main/README.md)）；OpenAgents Workspace（4.2k 星）让人在共享线程里 @Claude Code 和 Codex，2026 年 4 月在 V2EX、博客园面向中国开发者发布（〔原文〕[OpenAgents](https://github.com/openagents-org/openagents)；〔摘要〕[博客园](https://www.cnblogs.com/itech/p/19889215)）。

政策面在收紧。Anthropic 的支持地区不含中国大陆、香港和澳门，2025-09-04 起还禁止中资直接或间接控股超过 50% 的公司（含境外子公司）使用（〔原文〕[Anthropic 支持地区](https://www.anthropic.com/supported-countries)、[Anthropic 公告](https://www.anthropic.com/news/updating-restrictions-of-sales-to-unsupported-regions)）；阿里 2026-07-10 起内部禁用 Claude Code（〔摘要〕[TechCrunch](https://techcrunch.com/2026/07/04/alibaba-reportedly-bans-employees-from-using-claude-code/)）；OpenAI 同样不服务中国大陆和香港（〔摘要〕[SCMP](https://www.scmp.com/tech/policy/article/3267971/tech-war-openai-further-block-access-mainland-china-hong-kong-based-developers)）。开发者照用不误：一份 368 人的自选样本里 83% 用 Claude Code、78% 用 Codex（〔摘要〕[VibeCafe](https://vibecafe.ai/blogs/cn-coding-tools-2026)，样本自选），切换模型供应商的 cc-switch 有 139.8k 星、claude-code-router 有 37.5k 星（〔原文〕[cc-switch](https://github.com/farion1231/cc-switch)、[claude-code-router](https://github.com/musistudio/claude-code-router)），很多人保留 Claude Code 的外壳，把 `ANTHROPIC_BASE_URL` 指向国产模型。这对邻桌意味着三件事：身份不能挂在 Anthropic 或 OpenAI 账号上（规划已改用通行密钥）；工具面要对国产 CLI 中立，但国产 CLI 里调研只确认了 Kimi Code 有生命周期 hooks，其余都只确认支持 MCP；**中国侧成员大多拿不到厂商的 Team/Enterprise 账号**，所以厂商自家的团队功能天然缺掉中美混合团队的一半人（推断），这是邻桌少有的结构性机会。

两张表放在一起看，**邻桌独有的是组合，不是零件**。hooks 自动上报并不新：Emdash 会在 agent 的用户级配置里装生命周期 hooks 来跟踪状态和通知（〔原文〕[Emdash README](https://github.com/generalaction/emdash)），Warp 把 Claude Code 的 hook 事件映射成运行、阻塞、成功（〔二手〕[Yep Anywhere 的 Warp 评测](https://github.com/kzahel/yepanywhere/blob/main/docs/competitive/warp.md)），只是它们都是单人工具。「决定必须来自 agent 之外」也有先例：qm 把授权变更、冒充和命令审批排除在 agent 的 API 之外，理由是给 agent 留一条批准路径，就等于把人的闸门压成一次模型决定（〔原文〕[qm SECURITY.md](https://github.com/yc-software/qm/blob/main/SECURITY.md)）；Linear 的「负责人只能是人」、GitHub 的「agent 不能批准合并」是同一思路。跨人的困难对象最容易复制：Multica 有 `blocked` 状态和 `agent_blocked`，Paperclip 有带自动唤醒的 `blockedByIssueIds`，AAMP 有 `task.help_needed`。真正没有找到对应物的，是**逐条的「本人接受后才给自己的 agent」**：qm 的分类器隔离默认关闭、只管外部内容，Buzz 和 AAMP 只按作者或发件人放行，大平台靠仓库权限过滤或让模型把别人的话当「信息」。准确的说法是：在调研覆盖的范围内，邻桌是唯一把「各人自己的交互会话、跨人看板、agent 不能承诺、逐条接受」四件事放在一起的产品，而不是唯一做 hooks 或困难的产品。

小团队最可能的替代方案不是这十四个产品里的任何一个，而是「GitHub Issues、Linear 或 Jira，加它们的官方 MCP server，再在 CLAUDE.md、AGENTS.md 里写一句开工前先看工单」，一份 HN 讨论的摘要就说，多数团队的协作仍在 GitHub issue 和 PR 里（〔摘要〕[HN 47393964](https://news.ycombinator.com/item?id=47393964)）。这条路恰好是公开攻击最多的路径：2025 年 5 月 Invariant Labs 用公开仓库里的恶意 issue 经 GitHub MCP 偷出私有仓库数据（〔摘要〕[Invariant Labs](https://invariantlabs.ai/blog/mcp-github-vulnerability)），2025 年 6 月 Cato 用一张 Jira 服务台工单让内部工程师的 Claude 把其他工单的数据贴回给攻击者（〔摘要〕[Cato Networks](https://www.catonetworks.com/blog/cato-ctrl-poc-attack-targeting-atlassians-mcp/)），2026 年 4 月的 Comment and Control 用 issue 里不显示的 HTML 注释劫持了 Copilot 的 agent，GitHub 称之为「已知的架构局限」，只付了 500 美元赏金（〔原文〕[vectara 案例整理](https://raw.githubusercontent.com/vectara/awesome-agent-failures/main/docs/case-studies/comment-and-control-prompt-injection.md)，二手案例）。GitHub 自己的 MCP lockdown 模式只过滤没有 push 权限的作者，并写明它「不是授权边界」（〔原文〕[github-mcp-server 配置文档](https://github.com/github/github-mcp-server/blob/main/docs/server-configuration.md)）；在 2–5 人、人人都有写权限的私有仓库里，这层过滤等于没有（推断）。这是邻桌最有力的叙事，但要说清边界：调研没有找到私有小团队里「同事的 agent 在别处被注入，再把注入转述到看板上」的公开案例，这仍是前瞻风险。

量化最充分的团队痛点也值得对照。LinearB 2026 年基于 810 万个 PR 的基准显示，**AI 生成的 PR 等首次评审的时间是普通 PR 的 4.6 倍，30 天内合并率 32.7%，普通 PR 是 84.4%**（〔摘要〕[LinearB](https://linearb.io/resources/engineering-benchmarks)）；Stack Overflow 2025 年调查里只有 17% 的 agent 用户认为 agent 改善了团队协作（〔摘要〕[Stack Overflow 2025](https://survey.stackoverflow.co/2025/)）；对 2.5 万个 agent PR 的研究发现 79% 由同一个人既审又改，只有约八分之一的流程涉及不止一个人（〔摘要〕[LeadDev](https://leaddev.com/ai/ai-coding-agents-kill-team-collaboration)、[arXiv 2607.14037](https://arxiv.org/pdf/2607.14037)）；CooperBench 里两个 agent 协作的失败有 32% 是违背承诺或做出无法核实的声称（〔摘要〕[arXiv 2601.13295](https://www.arxiv.org/abs/2601.13295)）。前三组数据说明 agent 工作目前基本是单人游戏、评审排队是硬瓶颈，邻桌的「需要谁」应当覆盖「等谁 review」；最后一组支持把承诺留给人确认。

## 劣势是实打实的：没上线、一个人、Codex 只做过模拟

有明显劣势，而且不止一个。下表按对邻桌的伤害从大到小排；「邻桌现状」一列只写已经做出来的东西。

| 劣势 | 邻桌现状 | 对手现状 | 严重度 | 能不能补、在哪补 |
|---|---|---|---|---|
| 阶段：还没上线 | M0 原型加本地试用版，约 900 个自动测试；没有部署，通行密钥、真实通知、香港机都还没做；规划自己的判断是 M0「还不能定为通过」，Codex 的 S1、S2、S4、S6 和 S5、S7–S14 都待测（规划 §11.2） | Multica 从 2026-01-15 到 2026-10-01 发了 164 个 tag，云、桌面、自托管都能用（〔原文〕[Go proxy](https://proxy.golang.org/github.com/multica-ai/multica/@v/list)） | 高 | M1 的 12 个工作日加两周试点；期间不加范围 |
| Codex 一半没真测 | Claude Code 真机端到端验证过；Codex 只做过协议层模拟，而团队一半人用 Codex | Multica、Paperclip、Agor 都有 Codex 适配；Symphony 专做 Codex | 高 | 成员电脑补 S1、S2、S4、S6；把 M1 D8 的 Codex 试点当上线闸门（规划 §11.3） |

| 生态 | 只接 Claude Code 和 Codex；没有 GitHub、Linear、Jira 关联；飞书、钉钉、企业微信被用户明确排除（规划 §1.2） | Multica：26 种 CLI，GitHub、GitLab、Gitea、Forgejo 的 PR 关联，五种 IM（〔原文〕[GitHub 集成](https://raw.githubusercontent.com/multica-ai/multica/main/apps/docs/content/docs/github-integration.mdx)）；Symphony 接五种工单系统 | 中高 | GitHub PR 关联提前（第 5 节第 4 步）；其他 CLI 先走只用 MCP 的降级模式 |

| 商业模式 | 托管后端，没有任何付费意愿数据 | Terragon、Vibe Kanban Cloud 这类薄托管层已倒；大厂把多 agent 跟踪打包进现有订阅 | 高（长期） | 收费放在治理和信任上；先用设计伙伴验证 |

| 依赖未文档化接口 | Claude Code 的会话归属靠未文档化的 `_meta["claudecode/toolUseId"]`，Codex 的会话 ID 只在源码里（规划 §2.2、R6） | 自己跑 agent 的产品不依赖这些 | 中 | CI 金丝雀测试，失效时退回成员级（规划 R6） |

表里有两条比表面更深。第一条是**付费意愿完全没有被证明**：邻桌的共享看板需要托管后端，这正是 Terragon、Vibe Kanban Cloud 倒下时的形态，而大厂正把多 agent 跟踪打包进 Copilot、Cursor Teams 和 Claude Code 这些现有订阅，调研没有找到任何独立协调看板公开的定价或收入。第二条是**方向相反**：行业在减少人的确认。Anthropic 说 Claude Code 用户批准了 93% 的权限提示，并认为每个动作都认真手动批准「可以说是一种倒退」（〔原文〕[Anthropic：auto mode，2026-03-25](https://www.anthropic.com/engineering/claude-code-auto-mode)）；有经验的用户里超过 40% 的会话开着全自动批准（〔原文〕[Anthropic：agent 自主性，2026-02-18](https://www.anthropic.com/research/measuring-agent-autonomy)）；连 GitHub「请求者不能批准 agent 的 PR」这条规则，都有小团队在社区里抱怨（〔原文〕[GitHub 讨论 #179997](https://github.com/orgs/community/discussions/179997)）。邻桌逆着这个方向加确认，就必须证明每一次确认都值。规划已经把动作分成 T1（可在电脑上确认、10 分钟后才对 agent 生效）和 T2（只在确认设备上），并设了每天上限，方向是对的，但只有试点数据能证明代价可以接受。数据位置的问题对内部试用不大，对外卖给美国团队时会变成买家观感问题：规划 §10.4 已判断美国司法部的批量数据规则在目前规模下不构成受限交易，难点在「数据在香港、备份在上海」这句话本身。

## 对 Multica 真正难抄的只有「逐条接受」，而它恰恰最费事

把邻桌的差异点逐条摆到两类对手面前：一边是 Multica（同一目标、中国本土、发版最快），一边是大厂。

| 差异点 | 现状 | Multica 抄起来 | 大厂抄起来 | 判断 |
|---|---|---|---|---|
| hooks 接在各人自己的交互会话上，自动上报会话、进度和提交 | 已做（Claude Code 真测，Codex 模拟） | 容易：已有让自己会话操作看板的 CLI skill，加 SessionStart、Stop hooks 是增量工作（推断） | GitHub、Notion、Jira 可以经 MCP 或 API 收本地上报；Anthropic、OpenAI 不会为对家的 CLI 做 | 易抄；Emdash、Warp 已在单人工具里这样做 |
| 跨人的「谁卡住、需要谁」 | 已做 | 容易：已有 `blocked` 状态和 `agent_blocked` | 容易 | 易抄 |
| agent 令牌做不了承诺（403 human_only） | 已做 | 机制容易：已有受限的 run token；但和它「审批自动应答、无人值守」的默认设计相反 | 已有同类思路：Linear 负责人只能是人，GitHub 的 agent 不能批准合并 | 机制易抄，取舍难抄 |
| 同事写的正文要本人接受、别人 agent 的评论要本人转发，才进自己的 agent | 已做 | 难：@mention 直接触发 run、squad leader 自动唤醒成员，逐条接受会拆掉这套流程 | 难：GitHub 按写权限过滤，Claude Tag 靠模型把别人的话当「信息」；逐条接受和「一句话派活」冲突 | 最难抄，也最费事 |
| 通行密钥确认；电脑上确认的 10 分钟后才对 agent 生效 | 计划（M1） | 中：WebAuthn 本身不难，难在中国设备矩阵和找回流程 | 中：有能力做，但整个行业在减少确认 | 做对才算数 |
| 不经手模型流量；谁的订阅都能用；身份不绑厂商 | 已做（架构） | 已经如此：「Multica drives them; it doesn't ship them」 | Anthropic、OpenAI 的团队功能绑 Team/Enterprise 和自家 agent | 对两家模型厂商是结构性差异，对 Multica 不是 |
| 中美交付：香港部署、邮件加可选微信、按人时区和中美节假日 | 计划（M1 及之后） | 容易：香港公司、中文团队、已有国内 IM | 难：美国平台不会优先做 | 对大厂难抄，对 Multica 不算优势 |

结论有些反直觉。邻桌最容易讲清楚的卖点，「agent 自己汇报进度」「一眼看到谁卡住」，恰恰最容易被抄：Multica 已经有让自己会话操作看板的 CLI skill（〔原文〕[multica-cli README](https://raw.githubusercontent.com/multica-ai/multica-cli/main/README.md)）和不能碰敏感操作的 run token（〔原文〕[auth-tokens](https://raw.githubusercontent.com/multica-ai/multica/main/apps/docs/content/docs/auth-tokens.mdx)），按它大多数工作日都发版的节奏，加一个 hooks 接入模式在技术上不难（推断）。难抄的是取舍而不是代码：Multica 的执行模型建立在「审批自动应答、@mention 直接触发 run、squad leader 唤醒成员」之上，引入逐条接受会拆掉它自己的卖点；大厂的团队体验建立在「一句话派活」之上，Anthropic 和 OpenAI 也不会把对家的 agent 放进自己的团队视图、把团队功能下放给个人订阅。所以邻桌的护城河不在技术，而在「承诺只归人」这个立场能不能在真实团队里证明不拖慢工作。证明得了，这是一个对手不愿意（而不是不能）占的位置；证明不了，剩下的都是几周就能被抄走的零件。

## 先把两端跑通，再卖「人来答应」

### 先做什么：十步行动表

顺序的原则：先补会让整个论点不成立的缺口（Codex 真测、闸门代价），再补入场门票（GitHub 关联），然后才谈开源、定价和获客。每一步都落在规划已有的位置上。

| 顺序 | 时间 | 做什么 | 为什么 | 落在现有计划哪里 |
|---|---|---|---|---|
| 1 | 现在到 M1 第一周 | 把 Codex 一侧做成真测：在成员电脑上补 S1、S2、S4、S6，周验收 1 用真实 Codex 跑认领、进度、完成 | 一半成员用 Codex，现在只有协议层模拟；「两家对等」是相对 Anthropic、OpenAI 各自团队功能的核心差异 | 规划 §11.2（S1、S2、S4、S6）、§11.3 D5 和 D8 |
| 2 | M1（12 个工作日） | 按计划交付通行密钥、电脑上确认延迟 10 分钟生效、香港部署、邮件通知；硬规则 H1–H9 不砍 | 「人来答应」要有可验证的确认；调研覆盖的开源和创业产品里没有找到 WebAuthn 确认 | 规划 §11.3、D54–D56 |
| 3 | 上线后两周 | 把闸门的代价当成整个产品假设来测：在 11.5 的指标之外，单看每人每天的通行密钥次数、从通知到接受的中位时长、withheld 次数；按止损线决定是否继续 | 用户批准 93% 的权限提示，确认一多就变成反射动作；逐条接受是最难抄、也最可能被嫌烦的那一条 | 规划 §0 止损线、§11.5、R4 |
| 4 | M1 后 2–3 周 | GitHub 关联：提交和 PR 自动挂到任务；「等谁 review」作为困难的一种进「需要谁」，不新增 in_review 状态 | 量化最充分的痛点是评审排队；所有直接对手都有 PR 关联，这是入场门票 | 规划 §11.6「PR 检测」从「按信号」提前；§1.2 |
| 5 | M2 内拍板 | 开源客户端（CLI、hooks，Apache-2.0），公开威胁模型、硬规则和一部分注入回归语料；服务端暂不开源 | hooks 跑在每个成员的电脑上，「能审计上传了什么」本身是购买理由，也是最便宜的获客渠道 | 规划 §10.4、§11.7（原定 M3） |
| 6 | M2 | 其他 CLI 只走「只用 MCP、不自动上报」的降级模式，有试点需要再逐个验证 hooks，先验 Kimi Code | 国产 CLI 普遍支持 MCP，但更替快；追数量是 Multica 的主场 | 规划 §6.8 |
| 7 | M3 | 定位、定价、免费档上线（见下）；对外之前定运营主体，并准备第二个数据区域或自托管选项 | 美国买家可能介意「数据在香港、备份在上海」；收费和服务号要公司主体 | 规划 §10.4、§11.7、D63 |
| 8 | M3 | 找两个外部设计伙伴连续用 8 周，优先中美混合团队 | 目前没有任何付费意愿数据 | 规划 §11.7 验收 |
| 9 | M3 | 与 Linear、Jira、GitHub Issues 只同步标题、状态、负责人和链接，不同步正文 | 同步正文等于把闸门挡住的文字交给对方平台的 agent | 规划 §2.1 |
| 10 | 按信号 | 飞书或企业微信通知、自托管版、AAMP 桥 | 用户已排除飞书、钉钉、企微；AAMP 自 2026-07-29 没有提交 | 规划 §1.2 |

第 3 步是整张表的支点。规划的止损线（第 2 周结束时说「不方便」的人少于 2/4、自动化低于 30% 就停止投入 M2）已经很好，建议再加一条专门针对闸门的判断：如果电脑上的确认经常撞到每天 6 次的上限，或者「从通知到接受」的中位时长让请求协作比直接发微信还慢，就回到 D55 和信任档重新拍板，而不是在 M2 里继续堆功能。

### 不做什么

| 不做 | 为什么 |
|---|---|
| 自动执行、托管或拉起 agent | 这是大厂（Agent HQ、Linear coding sessions、Jira、Notion、CodeBuddy NPC）和 Multica、Paperclip、Symphony 的主场；托管算力正是 Terragon、Vibe Kanban Cloud 倒下时的成本结构；一旦替用户跑 agent，「人来答应」的定位就模糊了 |
| 通用工单系统 | Jira 10 人以下免费（〔二手〕[automationatlas](https://automationatlas.io/answers/jira-pricing-explained-2026/)），Linear 有免费档；做同步，不做替代 |
| 追 CLI 数量、squads、autopilots、甘特图 | Multica 已有 26 种 CLI 和这些功能，功能宽度是它的主场 |
| 在香港服务器上做服务端 LLM 摘要 | Anthropic、OpenAI 都不服务香港；规划 §10.4、§11.6 已有结论 |
| 经手模型流量、做中转 | Anthropic 消费者条款禁止共享账号和转售（〔原文〕[Consumer Terms](https://www.anthropic.com/legal/consumer-terms)）；社区的防封指南把共享账号列为封号高风险（〔原文〕[Claude-anti-ban](https://github.com/Fishason/Claude-anti-ban)） |
| 把闸门宣传成「防住了提示注入」 | 闸门只管同事文字这一条路，管不了外部网页、仓库配置和供应链：2026-09-02 披露的 GitSpawn 用 `.git/config` 在 7 个 CLI agent 里绕过沙箱和审批执行命令（〔摘要〕[The Hacker News](https://thehackernews.com/2026/09/malicious-git-configs-can-make-claude.html)），2026 年 2 月的 Clinejection 从一个 issue 标题一路打到约 4,000 台开发者电脑（〔摘要〕[Adnan Khan](https://adnanthekhan.com/posts/clinejection/)）；GitHub 也承认自己的过滤「不是授权边界」 |
| 拿 Multica、Agor 的代码做托管产品 | 许可证禁止（见第 1 节） |
| M1 加飞书、钉钉、企业微信 | 用户已明确排除（规划 §1.2）；只有对外面向国内本土团队、且有客户点名要时再评估 |

### 定位：agent 汇报，人来答应

一句话：**「邻桌：agent 汇报进度，人来答应别人。」**英文可以写成「Longtable: your agents report, people commit.」目标客户是 2–10 人的软件团队，成员已经各自付费用 Claude Code 或 Codex（混用最好），以交互式结对为主而不是 24 小时自动驾驶，跨时区（尤其中美）或者在意「同事的文字劫持自己的 agent」。明确不面向两类人：想把工单丢给 agent 自己做完的团队，Agent HQ、Linear coding sessions、Multica 更合适；一个人同时开二十个 agent 的人，Conductor、Paperclip 更合适，Paperclip 的 README 就把「你同时开着 20 个 Claude Code 终端」写成目标用户（〔原文〕[Paperclip README](https://raw.githubusercontent.com/paperclipai/paperclip/master/README.md)）。面对不同对手，说法各不相同：

| 面对 | 一句话区别 | 依据 |
|---|---|---|
| Multica、Paperclip、Symphony | 我们不替你跑 agent，也不让 agent 替你答应；Multica 默认用 `bypassPermissions` 跑 Claude Code 并自动应答审批，Symphony 示例配置是 `approval_policy: never` | 〔原文〕[Multica 安全模型](https://raw.githubusercontent.com/multica-ai/multica/main/apps/docs/content/docs/security-model.mdx)、[Symphony WORKFLOW](https://github.com/openai/symphony/blob/main/elixir/WORKFLOW.md) |
| GitHub、Linear、Jira、Notion | 它们管云端运行和工单；我们管各人本机会话在做什么、谁在等谁，并在同事文字进 agent 之前加一道人的关；和它们同步，不替代它们 | 表 2 |
| Anthropic、OpenAI | 混合团队里，任何一家的团队功能都看不到另一家的 agent，而且大多要 Team/Enterprise 账号，中国侧成员拿不到 | 〔原文〕[Claude Tag 概览](https://claude.com/docs/claude-tag/overview)、[Anthropic 支持地区](https://www.anthropic.com/supported-countries) |
| AQ、HumanLayer 等共享会话产品 | 我们共享的是承诺和状态，不是键盘；「谁都能打字」「访客能处理审批」会扩大注入面 | 〔摘要〕[aq.dev](https://aq.dev/)；〔二手〕[Yep Anywhere 评测](https://github.com/kzahel/yepanywhere/blob/main/docs/competitive/multiplayer-ai.md) |

### 获客：用试点数据和安全透明度换信任

获客先要解决「零星、零用户、没人听说过」。最有说服力的第一件素材是邻桌自己的试点数据：把规划 §11.5 的接入健康、自动化、协作闭环和「不吵」四项指标，加上「少问一次、少等一次」的实例，写成一篇公开的中美小团队两周报告，这比任何功能列表都更能证明「人来答应」不拖慢工作。第二件是开源客户端和安全文档：hooks 跑在每个成员的电脑上，而 GitSpawn、Clinejection 这类事件让「能审计上传了什么」成了真实的购买理由；公开威胁模型、服务端强制的硬规则和一部分注入回归语料的同时，要写清闸门挡不住什么，过度宣传会反噬。第三件是渠道：英文社区用 Show HN，中文社区用 V2EX、LINUX DO、掘金、博客园，OpenAgents 就是在 V2EX 和博客园向中国开发者发布的，AgentBridge 也在 LINUX DO 上被讨论（〔原文〕[AgentBridge](https://github.com/raysonmeng/agent-bridge)）；再申请进入 awesome-agent-orchestrators 这类清单，它正是本次调研发现项目的主要入口。第四件是设计伙伴：M3 的验收本来就要求两个外部团队连续用 8 周（规划 §11.7），优先从创始人身边的中美混合团队找，用免费换每周一次访谈。以后有了 PR 关联，GitHub Marketplace 是自然的发现入口；Claude Code 插件市场可以只当发现入口，安装仍走 `teamflow setup`，因为规划 §1.2 记录过插件下发不了 env。

### 出现这些信号就回头改判断

| 信号 | 说明什么 | 怎么办 |
|---|---|---|
| Multica 文档出现 hooks 接入模式，或 CLI skill 改用受限 token | 「接在自己会话上」不再独有 | 宣传重心全部转到逐条接受和承诺确认；加快开源和试点案例 |
| Notion External Agents 或 Jira 的 agent 会话开放本地会话上报 | 大平台进入本地会话 | 做它们的同步伙伴，只同步标题、状态和链接 |
| Anthropic agent teams 支持跨机器、跨人，或 Codex 发布规划 §2.1 记录的、源码里在开发的 agent_message_board | 厂商把团队协调做进 CLI | 评估做成它们的适配层 |

| 电脑上确认经常撞到每天 6 次的上限，或出现「不是我」的撤销 | 闸门代价过高，或有人被诱导确认 | 回到 D55 请 owner 重新拍板，调整信任档 |

## 结论

竞争的轴线已经从「能不能让 agent 上看板」移到了「谁有权替团队答应」。执行在变便宜，所有人都在放权：Copilot 已能在开启后批准 PR，Claude Code 有 auto mode，Multica 默认自动应答审批。稀缺的反而是可审计、可追责的人类承诺；CooperBench 里约三成的协作失败属于 agent 违背承诺或做出无法核实的声称，这不会因为模型变强就自动消失。所以邻桌要卖的不是又一块看板，而是一条规则：agent 可以干活、可以汇报，答应别人的事只能由人来做，同事的文字要你点头才进你的 agent。小团队最顺手的替代方案（工单系统加官方 MCP）恰好就是公开攻击最多的路径，这给了这条规则一个现成的故事，只是要诚实地承认，私有小团队里的转述注入还没有公开案例。

讽刺的是，这条规则里唯一难抄的部分，正是摩擦最大的部分。这让 M1 之后的两周试点不只是功能验收，而是对整个产品论点的判决：数据表明闸门可以接受，邻桌就站在一个 Multica 和大厂不愿意（而不是不能）占的位置上，接下来比的是速度、信任口碑和中美交付的细节；数据表明闸门太重，剩下的 hooks 上报和困难对象都是几周就能被抄走的零件，应该按规划的止损线及早收手，或者把它们做成别人平台上的一个插件。
